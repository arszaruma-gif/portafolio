TEMA 01
Clasificación General de las Pruebas
⚙️
Funcionales vs. No Funcionales

⚙️ Pruebas FUNCIONALES

Verifican QUÉ hace el sistema — si las funciones cumplen los requisitos especificados.

  • ¿El login acepta credenciales correctas?
  • ¿El cálculo de descuento es correcto?
  • ¿Se envía el correo de confirmación?
  • ¿Se guardan los datos en la BD?

📊 Pruebas NO FUNCIONALES

Verifican CÓMO se comporta — calidad de operación: velocidad, seguridad, usabilidad.

  • ¿Responde en < 2 segundos?
  • ¿Soporta 10.000 usuarios simultáneos?
  • ¿Es fácil de usar para un novato?
  • ¿Resiste un ataque SQL injection?
🔍
Otra Dimensión: Estáticas vs. Dinámicas
  • ESTÁTICAS: No se ejecuta el código. Se revisan documentos, requisitos, código fuente y diseño.
    Ej: Revisiones · Inspecciones · Análisis estático · Walkthroughs
  • DINÁMICAS: Se ejecuta el software con entradas y se observan las salidas reales del sistema.
    Ej: Pruebas unitarias · Integración · Sistema · UAT · Regresión

TEMA 02
Pruebas por Caja: Negra, Blanca y Gris
Tipo de Caja Descripción Técnicas Comunes ¿Quién lo hace?
⬛ Caja NEGRA
Black Box Testing		 El tester no conoce el código interno. Prueba basada en entradas/salidas y requisitos funcionales. Partición de equivalencias, Valores límite, Tabla de decisiones, Casos de uso. QA Testers, usuarios
⬜ Caja BLANCA
White Box / Glass Box		 El tester conoce la estructura interna. Diseña casos para cubrir caminos, ramas y condiciones. Cobertura de sentencias, Cobertura de ramas, Complejidad ciclomática, Caminos. Desarrolladores, QA técnico
🔲 Caja GRIS
Grey Box Testing		 Combina enfoques: acceso parcial a arquitectura o BD sin conocer el código completo. Pruebas de integración, API, Análisis de arquitectura, Seguridad web. QA Engineer Senior, DevOps

TEMA 03
Pruebas Funcionales — Los 4 Niveles

1. Pruebas Unitarias

  • Alcance: Función / Método individual
  • Cuándo: Durante el desarrollo, por el propio dev
  • 💡 Ejemplo: Probar que calcularIVA(100) retorna 12.00
  • 🛠 Herramientas: JUnit, NUnit, PyTest, Jest, Mocha

2. Pruebas de Integración

  • Alcance: Interacción entre módulos
  • Cuándo: Al combinar componentes o servicios
  • 💡 Ejemplo: Probar que el módulo de pagos se comunica correctamente con la BD
  • 🛠 Herramientas: Postman, REST Assured, TestNG, Cucumber

3. Pruebas de Sistema

  • Alcance: Sistema completo end-to-end
  • Cuándo: Después de la integración, antes de UAT
  • 💡 Ejemplo: Probar flujo: registro → pedido → pago → confirmación
  • 🛠 Herramientas: Selenium, Cypress, TestComplete, Robot Framework

4. Pruebas de Aceptación (UAT)

  • Alcance: Validación del negocio por el cliente
  • Cuándo: Antes de la entrega formal al cliente
  • 💡 Ejemplo: El cliente verifica que el sistema cumple los criterios del contrato
  • 🛠 Herramientas: Cucumber, FitNesse, Excel/manual

TEMA 04
Pruebas No Funcionales
Evalúan CÓMO funciona el sistema, no qué hace — calidad de servicio.

⚡ Rendimiento (Performance)

Tiempo de respuesta, throughput, uso de recursos bajo carga normal.

🛠 JMeter, Gatling, k6

📈 Carga (Load)

Comportamiento con volumen creciente hasta el punto de rotura.

🛠 JMeter, Locust, BlazeMeter

💥 Estrés (Stress)

Qué pasa al superar carga máxima. Punto de quiebre y recuperación.

🛠 Gatling, k6, Artillery

🔒 Seguridad (Security)

Vulnerabilidades, autenticación, autorización, inyecciones, cifrado.

🛠 OWASP ZAP, Burp Suite, Nessus

👤 Usabilidad (Usability)

Facilidad de uso, interfaz intuitiva, experiencia del usuario final.

🛠 UserTesting, Hotjar, SUS Score

🌐 Compatibilidad

Funciona en distintos navegadores, SO, dispositivos y versiones.

🛠 BrowserStack, Sauce Labs, LambdaTest

TEMA 05
Pruebas de Regresión, Humo y Sanidad

🔄 Prueba de REGRESIÓN

  • ¿Cuándo?: Cada vez que se modifica el código.
  • Objetivo: Verificar que los cambios no rompieron funcionalidades que ya trabajaban.
  • Proceso: Ejecutar suite completa de tests existentes tras cada cambio.
  • Automatiz.: ★★★ Alta — Ideal para automatizar (Selenium, Cypress, pytest).
  • Ejemplo: Al añadir módulo de descuentos, se re-ejecutan todos los tests de facturación.

💨 Prueba de HUMO (Smoke)

  • ¿Cuándo?: Al recibir un nuevo build del sistema.
  • Objetivo: Verificar que las funciones más críticas funcionan — 'prende o no prende'.
  • Proceso: Ejecutar subconjunto reducido (10-20%) de tests críticos. Rápido (<30 min).
  • Automatiz.: ★★★ Alta — Primer gate de CI/CD.
  • Ejemplo: ¿El sistema inicia? ¿El login funciona? ¿La página carga?

🩺 Prueba de SANIDAD

  • ¿Cuándo?: Después de un bug fix específico.
  • Objetivo: Verificar que una corrección funciona y no causó efectos secundarios cercanos.
  • Proceso: Subconjunto focalizado en el área del fix. Más profundo que humo, más rápido que regresión.
  • Automatiz.: ★★ Media — A veces manual para mayor foco.
  • Ejemplo: Se corrigió bug en impuestos. Se prueba solo el módulo fiscal.

Ejercicio 2 — Identificar el Tipo de Prueba según el Escenario
  • A. Dev verifica calcularPromedio() [6, 8, 9] retorna 7.5. → Prueba Unitaria (Caja BLANCA)
  • B. QA ejecuta 250 tests tras fix en pagos para ver que no se rompió nada. → Prueba de Regresión (Caja Negra/Gris)
  • C. Operaciones simula 5.000 usuarios concurrentes en e-commerce. → Prueba de Carga/Estrés (Caja NEGRA)
  • D. QA Lead ejecuta 15 casos críticos antes de aceptar el build. → Prueba de Humo / Smoke (Caja NEGRA)
  • E. Ministerio revisa flujos según pliegos de requerimiento. → Prueba de Aceptación / UAT (Caja NEGRA)
  • F. Security tester inyecta payloads SQL y XSS. → Prueba de Seguridad (Caja GRIS)

Descripción del Escenario ① Tipo de Prueba ② Tipo de Caja Justificación
Escenario G
El equipo de QA verifica que los datos de compra generados en la tienda virtual se transmitan de forma correcta y en el formato estructurado correspondiente hacia la API de la pasarela de pagos externa (como Stripe o PayPal).		 Prueba de Integración Caja GRIS Se enfoca en la comunicación y el intercambio de datos entre sistemas. El tester no ve el código de la API, pero conoce y manipula la estructura de mensajes XML o JSON.
Escenario H
Se convoca a un grupo de usuarios reales (por ejemplo, adultos mayores) para evaluar si la nueva interfaz de una aplicación de salud es intuitiva y si son capaces de agendar una cita médica en menos de 3 pasos sin recibir asistencia técnica.		 Prueba de Usabilidad Caja NEGRA Evalúa qué tan fácil, eficiente y agradable es el sistema para el usuario final. Se basa en la interacción externa con la interfaz gráfica, ignorando el código.
Escenario I
El tester ejecuta de forma sistemática la plataforma web en múltiples navegadores (Chrome, Safari, Firefox, Edge) y dispositivos móviles con diferentes tamaños de pantalla (iOS y Android) para asegurar que el diseño responsivo no se desconfigure.		 Prueba de Compatibilidad Caja NEGRA Verifica que el software funcione de manera correcta en distintos entornos, hardware y navegadores, analizando el comportamiento visual expuesto al usuario.
Escenario J
El desarrollador utiliza una herramienta especializada de análisis dinámico para comprobar que sus pruebas automatizadas de código alcancen a recorrer el 100% de las ramas condicionales (if/else) de un algoritmo que calcula impuestos según la región.		 Prueba de Cobertura (Estructural) Caja BLANCA Mide qué porcentaje del código fuente está siendo ejecutado. Requiere acceso total a la lógica, sentencias y caminos del flujo interno de la programación.

📝 ENUNCIADO — Estrategia de Pruebas para un Sistema de Inventario
Una empresa de logística y retail va a lanzar un nuevo sistema web de gestión de inventarios para centralizar el control de sus bodegas. Para cada módulo, se debe diseñar la estrategia de pruebas indicando: tipo de prueba, tipo de caja, herramienta recomendada y criterio de éxito.

Módulo Tipo de Prueba Caja Herramienta Criterio de Éxito
Cálculo de valoración de stock
(Fórmulas de costo promedio ponderado, mermas y alertas de stock mínimo)		 Unitaria Blanca JUnit / PyTest Retorna el valor monetario exacto del inventario y dispara alertas automáticas según los rangos establecidos.
API de Proveedores y Facturación
(Sincronización de órdenes de compra con sistemas externos)		 Integración Gris Postman / RestAssured Datos del proveedor y stock entrante sincronizados correctamente en < 3s, retornando código 200 OK.
Flujo de Entrada y Egreso de Mercancía
(La aplicación web completa desde la recepción del producto hasta su despacho)		 Sistema Negra Selenium / Cypress Todos los flujos críticos de la interfaz de usuario (crear, editar, mover y dar de baja stock) funcionan de extremo a extremo (end-to-end).
Importación masiva de catálogo
(Subida simultánea de archivos con más de 10,000 códigos de barra)		 Carga Negra JMeter / k6 Procesamiento completo del archivo masivo en < 5s bajo condiciones de alta demanda, con 0% de pérdida de datos.
Roles de usuario y logs de auditoría
(Control de quién puede modificar el inventario)		 Seguridad Gris OWASP ZAP Un usuario con rol de "Operador de Bodega" no puede alterar precios base ni borrar el historial de auditoría (0 vulnerabilidades críticas).
Validación del Jefe de Almacén
(Uso del sistema en el día a día)		 UAT Negra Pruebas Manuales / Jira El Jefe de Almacén valida que los flujos diarios se ejecuten de forma fluida, intuitiva y conforme a los requisitos del negocio.

CIERRE
Resumen — Semana 7
💡
Puntos clave
  • 01. Las pruebas se clasifican en Funcionales (qué hace) y No Funcionales (cómo lo hace). Ambas imprescindibles.
  • 02. Caja Negra prueba sin conocer el código (usuario). Caja Blanca requiere conocimiento interno.
  • 03. Los 4 niveles funcionales (Unitaria → Integración → Sistema → UAT) se ejecutan en ese orden.
  • 04. Rendimiento, Seguridad y Usabilidad son pruebas no funcionales críticas desde el inicio.
  • 05. Regresión = no romper lo que ya funcionaba. Humo = build válido. Sanidad = fix correcto.
