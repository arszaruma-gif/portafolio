Aplicación de Pruebas de Software · Del plan a la ejecución: aplicar pruebas reales en proyectos reales

TEMA 01
El Proceso Completo de Aplicación de Pruebas
🔄
Fases del Ciclo de Pruebas
📋 1. PLANIFICACIÓN: Define alcance, objetivos, recursos y estimaciones. (Entregable: Plan de Pruebas)
✏️ 2. DISEÑO: Crear casos de prueba, definir datos de entrada y priorizar. (Entregable: Casos de Prueba)
⚙️ 3. PREPARACIÓN: Configurar ambiente, herramientas y ejecutar pruebas de humo. (Entregable: Ambiente Listo)
▶️ 4. EJECUCIÓN: Ejecutar casos, registrar resultados, reportar bugs. (Entregable: Defect Reports)
📊 5. ANÁLISIS y CIERRE: Calcular métricas, evaluar criterios Go/No-Go. (Entregable: Informe de Calidad)
📝
Mis apuntes

    • 1. Planificación (Planning) — Definición Estratégica

    📝 CONTEXTO: Fase inicial que establece el rumbo del proyecto de aseguramiento de calidad, respondiendo formalmente al "por qué", "qué", "cuándo" y "quién" de las pruebas.

    Entradas Adicionales Entregables Clave (Outputs) Estrategia y Valor Añadido
    • Criterios de aceptación iniciales.
    • Acuerdos de nivel de servicio (SLA).
    • Plan de Pruebas (Test Plan): Estrategia, alcance, recursos y cronograma maestro.
    • Matriz de Estimación: Cálculo de horas/hombre requeridas.
    • Matriz de Riesgos de Calidad: Planes de mitigación ante riesgos del producto.
    		 Definición del Core de Pruebas: Se dictaminan los enfoques de prueba requeridos (manual, automatización, rendimiento, seguridad, etc.) alineándolos con los objetivos del negocio.
    # Definición conceptual de la Planificación del Proyecto
    fase_planificacion = {
        "estrategia": "Establecer alcance, recursos, presupuesto y tiempos clave",
        "entregable_maestro": "Test_Plan_v1.0.pdf",
        "enfoques": ["Manual", "Automatizado", "Performance", "Security"]
    }

    • 2. Diseño (Design) — Estructura Técnica de Pruebas

    📝 CONTEXTO: Fase encargada de materializar los requerimientos funcionales y de negocio en especificaciones técnicas de prueba detalladas que guiarán la ejecución.

    Entradas Adicionales Entregables Clave (Outputs) Estrategia y Valor Añadido
    • Prototipos de UI/UX.
    • Arquitectura técnica del sistema.
    • Casos de Prueba: Paso a paso detallado con datos de entrada y resultados esperados.
    • Matriz de Trazabilidad (RTM): Mapeo exhaustivo Requisito-Caso.
    • Escenarios de Prueba: Ideas de alto nivel sobre los flujos del sistema.
    		 Garantía de Cobertura: La RTM asegura una cobertura lógica del 100% sobre las necesidades del negocio antes de iniciar código.
    # Estructura del diseño y cobertura del software
    fase_diseno = {
        "casos_de_prueba": ["TC-001_LoginExitoso", "TC-002_LoginInvalido"],
        "trazabilidad_rtm": "Requisito_Funcional_01 <---> TC-001",
        "cobertura_esperada": "100% de especificaciones mapeadas"
    }

    • 3. Preparación / Configuración del Entorno (Test Environment Setup)

    📝 CONTEXTO: Aprovisionamiento, estabilización y despliegue de la infraestructura donde se llevarán a cabo las pruebas de manera segura y controlada.

    Entradas Adicionales Entregables Clave (Outputs) Estrategia y Valor Añadido
    • Manuales de despliegue de software.
    • Scripts de bases de datos relacionales/NoSQL.
    • Ambiente de Pruebas Listo: Redes, servidores e infraestructura estabilizada.
    • Datos de Prueba (Test Data): Base de datos sembrada con registros válidos.
    • Reporte de Smoke Test: Validación rápida que confirma la estabilidad del ambiente.
    		 Estabilidad de Fase: Mitiga falsos positivos causados por discrepancias infraestructurales frente a entornos de producción.
    # Verificación de integridad del entorno de QA
    verificar_entorno = {
        "ambiente": "qa-env-v12",
        "datos_cargados": ["UsuariosFicticios", "TarjetasPrueba", "StockInventario"],
        "smoke_test": "PASSED (Ambiente listo para ejecución de pruebas)"
    }

    • 4. Ejecución (Execution) — Detección Activa de Fallos

    📝 CONTEXTO: Ciclo dinámico donde se corren los casos de prueba diseñados, contrastando el software contra el comportamiento esperado y documentando discrepancias.

    Entradas Adicionales Entregables Clave (Outputs) Estrategia y Valor Añadido
    • Acceso a herramientas ALM o de defectos (Jira, Azure DevOps, Bugzilla).
    • Registro de Ejecución (Log): Evidencia histórica de corridas de prueba.
    • Reporte de Defectos (Bugs): Tickets estructurados con evidencias de fallos.
    • Suite de Regresión: Selección de casos de prueba para mitigar efectos colaterales.
    		 Localización de Errores: Los reportes detallados y categorizados permiten al equipo de desarrollo realizar depuraciones rápidas y precisas.
    # Reporte simplificado de un Defecto (Bug)
    defecto_reportado = {
        "id": "BUG-2026-01",
        "titulo": "Error 500 al procesar pago con saldo exacto",
        "pasos": "1. Agregar producto de $100 -> 2. Pagar -> 3. Error en pasarela",
        "evidencias": ["log_consola.txt", "captura_pantalla.png"]
    }

    • 5. Análisis y Cierre (Test Closure & Analysis) — Evaluación de Calidad

    📝 CONTEXTO: Fase de balance e informe final donde se consolidan métricas clave del proyecto para recomendar o autorizar el despliegue del producto a producción.

    Entradas Adicionales Entregables Clave (Outputs) Estrategia y Valor Añadido
    • Acuerdos de "Definition of Done" (DoD).
    • Informe de Cierre (Test Summary): Reporte gerencial de calidad y dictamen.
    • Métricas de Calidad: Densidad de defectos, porcentaje de aprobación y DRE.
    • Lecciones Aprendidas: Documento de mejora continua (Retrospectiva).
    		 Toma de Decisiones Informadas: Transfiere datos objetivos sobre el nivel de riesgo del software al equipo de negocio para avalar el lanzamiento.
    # Métricas fundamentales de Calidad en Cierre
    metricas_finales = {
        "porcentaje_aprobacion": "97.4%",
        "densidad_defectos": "0.15 fallos por caso ejecutado",
        "efectividad_remocion_dre": "92.0% (Defectos mitigados antes de producción)",
        "recomendacion": "GO (Cumple criterios del DoD de Calidad)"
    }

TEMA 02
Plan de Pruebas — Estructura IEEE 829
📄
Componentes Clave del Plan
  • Identificador y Alcance: Funcionalidades incluidas (in-scope) y excluidas (out-of-scope).
  • Estrategia de Prueba: Niveles, técnicas manuales/automáticas y herramientas.
  • Criterios de Entrada/Salida: Cuándo empezar (ej. build estable) y cuándo terminar (ej. 0 críticos, 80% coverage).
  • Recursos y Cronograma: Equipo QA, ambientes requeridos y fechas hito.
  • Riesgos y Contingencias: Identificar posibles bloqueos y plan de mitigación.
  • Entregables: Qué documentos se generarán al final (Test Closure Report).
📝
Mis apuntes

    1. Identificador y Alcance

    Detalle IEEE 829: Originalmente se dividía en Test Plan Identifier, Introduction, Test Items (módulos a probar) y Features to be Tested / Features not to be Tested.

    Información para complementar:

    • Features NOT to be tested (Fuera de alcance): Es tan importante detallar lo que no se va a probar como lo que sí. Por ejemplo: "No se probará la pasarela de pagos externa ya que depende de un proveedor tercero, ni se realizarán pruebas de rendimiento en esta fase". Esto evita falsas expectativas con los stakeholders.
    • Referencias: Incluir enlaces o versiones exactas de los documentos origen (Historias de Usuario, SRS, Diagramas de Arquitectura) para saber en qué nos basamos.

    2. Estrategia de Prueba

    Detalle IEEE 829: Se conocía formalmente como la sección Approach.

    Información para complementar:

    • Criterios de Priorización: Explicar cómo se decidirá qué probar primero (ej. técnicas basadas en riesgos o las funcionalidades más críticas del negocio).
    • Configuraciones de Entorno Soportadas (Matriz de Compatibilidad): Detallar los sistemas operativos, navegadores (Chrome, Safari, Edge) y dispositivos móviles específicos en los que se ejecutará la estrategia.

    3. Criterios de Entrada/Salida

    Detalle IEEE 829: Se desglosaba en Item Pass/Fail Criteria y Suspension Criteria and Resumption Requirements.

    Información para complementar:

    • Criterios de Suspensión: ¿Cuándo detenemos las pruebas por completo? Ejemplo: Si el módulo de login falla y bloquea el acceso a toda la aplicación, las pruebas se suspenden inmediatamente.
    • Criterios de Reanudación: ¿Qué debe pasar para volver a testear tras una suspensión? Ejemplo: Que el equipo de desarrollo entregue un parche que solucione el bloqueador y pase un Smoke Test exitoso.

    4. Recursos y Cronograma

    Detalle IEEE 829: Incluía Staffing and Training Needs, Responsibilities y Schedule.

    Información para complementar:

    • Necesidades de Capacitación (Training): Si el sistema requiere usar herramientas nuevas (ej. Playwright, JMeter) o entender un modelo de negocio complejo (ej. contabilidad bancaria), se debe agendar un tiempo previo de capacitación para los testers.
    • Matriz de Responsabilidades (RACI): Definir claramente quién aprueba los casos, quién los ejecuta, quién gestiona el entorno y quién prioriza los bugs.

    5. Riesgos y Contingencias

    Detalle IEEE 829: Se denominaba Risks and Contingencies.

    Información para complementar:

    Riesgos Comunes de QA y su mitigación:

    • Riesgo: Retraso en la entrega del software por parte de desarrollo.
      Contingencia: Reducir el alcance de pruebas (probar solo flujos críticos) o automatizar casos clave para acelerar la ejecución.
    • Riesgo: Indisponibilidad o inestabilidad del ambiente de pruebas.
      Contingencia: Tener un ambiente espejo (Staging) listo o usar mocks de servicios caídos.

    6. Entregables del Testing

    Detalle IEEE 829: El estándar original no solo listaba los entregables, sino que definía formatos estructurales para cada uno de ellos (Test Case Specification, Test Incident Report, etc.).

    Información para complementar:

    • Evidencias de Prueba: Especificar en qué formato y dónde se guardarán las evidencias (capturas de pantalla, grabaciones de video, logs de base de datos) para fines de auditoría.
    • Frecuencia de Reportes: Indicar cada cuánto se enviarán actualizaciones (ej. Reporte de avance diario de ejecución vía Slack/Correo y Reporte de Cierre final al terminar el ciclo).

TEMA 04
Gestión de Defectos en la Práctica
🐛
Clasificación de Defectos (Severidad)
  • 🔴 CRÍTICO: El sistema no funciona, pérdida de datos. Bloquea pruebas. No negociable.
  • 🟠 ALTO: Funcionalidad principal rota. Workaround posible pero difícil.
  • 🟡 MEDIO: Funcionalidad secundaria afectada. Workaround disponible y sencillo.
  • 🟢 BAJO: Problema cosmético, textos, o usabilidad menor. No impide el uso.
📋
Ejemplo de Reporte (Bug Ticket) 
ID Defecto:  BUG-0042
Título:      Nota mayor a 10 es aceptada en Registro de Notas
Severidad:   🔴 CRÍTICO
Prioridad:   P1 — Inmediata
Pasos reproducir: 
  1. Ingresar nota=11
  2. Click Guardar
Esperado:    Error: 'Nota debe estar entre 0 y 10'
Obtenido:    Nota 11 guardada. Sin mensaje de error.
Asignado a:  Dev: Carlos Mendoza

TEMA 05
Estrategias de Automatización y Métricas
🤖
¿Qué automatizar y qué NO?
SÍ Automatizar:
  • Tests repetitivos (Regresión).
  • Pruebas de carga y rendimiento.
  • Data-driven tests (múltiples datos).
NO Automatizar:
  • UX subjetiva y usabilidad.
  • Exploratory testing (requiere intuición).
  • Funciones que cambian constantemente.
📊
Métricas Clave de la Ejecución
Métrica Fórmula Meta Ideal
Tasa de Ejecución (Casos ejecutados / Total planificados) × 100 > 95%
Tasa de Aprobación (Casos PASS / Total ejecutados) × 100 > 85%
Densidad de Defectos Defectos encontrados / KLOC < 1
MTTR Tiempo promedio de corrección < 48h

E1: Plan de Pruebas Sistema Biblioteca IST

  • Criterios de Entrada/Salida: Inicia con build estable; Termina con 0 críticos, >85% PASS y >80% coverage.
  • Tipos: Unitarias (multas), Integración (flujo BD), Sistema (e2e), UAT (con bibliotecario).
  • Riesgos: Requisitos incompletos (revisión temprana), Tiempo (priorizar casos críticos).

E3: Análisis Integral (Go / No-Go)

Datos: Plan=80, Ejec=74, PASS=62, Críticos=3, Cov=71%

  • Ejecución: 74/80 = 92.5% (Aceptable)
  • Aprobación: 62/74 = 83.8% (⚠️ Requiere análisis)
  • Cobertura: 71% (❌ Insuficiente, meta ≥80%)
  • Decisión Go/No-Go: NO-GO (Existen 3 defectos críticos abiertos).

CIERRE
Resumen de la Semana 9
💡
Puntos clave
  • La aplicación de pruebas requiere disciplina en sus 5 fases. Saltar el diseño genera caos.
  • El Plan de Pruebas (IEEE 829) es el documento rector; sin él, no hay dirección.
  • Los defectos críticos bloquean entregas. La decisión Go/No-Go es basada en datos y métricas (≥85% PASS, 0 Críticos), no en intuición.
  • La automatización debe enfocarse en regresión, datos y rendimiento.
