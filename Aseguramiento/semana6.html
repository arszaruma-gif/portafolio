Mis apuntes

01. ¿Por qué Probamos Software? (Definición de prueba, mitos vs. realidad y la regla del costo temprano)
• Ejemplo 1 (Mito vs. Realidad): Romper el mito de que "las pruebas demuestran que el software no tiene errores". En la realidad, si pruebas una aplicación móvil de un banco y no encuentras fallas, solo demuestra que pasó los escenarios ejecutados, pero no garantiza al 100% que no existan errores ocultos bajo otras condiciones.
• Ejemplo 2 (Regla del costo temprano): Si un analista detecta una contradicción en los requerimientos escritos de una pantalla antes de que se programe, corregirla cuesta casi $0. Si el error se deja pasar, se programa mal y el cliente lo descubre en producción, el costo de corregirlo se multiplica drásticamente por todo el retrabajo necesario.

02. El Costo de No Probar (Casos reales de fallos por falta de pruebas y su impacto económico)
• Ejemplo 1 (Impacto Espacial): El caso histórico del cohete Ariane 5 (1996), el cual exploded 37 segundos después de despegar debido a un error de software no detectado (desbordamiento de entero), lo que provocó una pérdida de $370 millones de dólares.
• Ejemplo 2 (Impacto en la Salud): El desastre de la máquina de radioterapia médica Therac-25, donde la ausencia de pruebas de concurrencia de software causó una condición de carrera que terminó costando 6 vidas humanas debido a sobredosis masivas de radiación.

03. Principios Fundamentales del Testing (Los 7 principios del testing según ISTQB)
• Ejemplo 1 (Principio: Las pruebas exhaustivas son imposibles): Tratar de probar un campo de texto que acepta contraseñas de hasta 20 caracteres combinando todas las letras, números y símbolos existentes. Como las combinaciones tienden al infinito, los testers aplican técnicas para elegir solo los valores más representativos.
• Ejemplo 2 (Principio: Paradoja del Pesticida): Si un equipo ejecuta exactamente los mismos casos de prueba manuales mes tras mes en una plataforma web, llegará un punto en que esas pruebas ya no detectarán nuevos defectos, obligando a los ingenieros a actualizar y diseñar nuevos escenarios.

04. Tipos y Niveles de Prueba (Unitarias, integración, sistema, aceptación)
• Ejemplo 1 (Prueba Unitaria): Un desarrollador escribe un pequeño bloque de código aislado para verificar de forma matemática y estricta que la función calcularDescuento(100, 10%) retorne exactamente el valor numérico 90.
• Ejemplo 2 (Prueba de Aceptación): Antes de firmar el contrato de cierre, el dueño de una cadena de supermercados realiza simulaciones de compras reales en el sistema de facturación recién desarrollado para validar si el producto cumple formalmente con todas sus necesidades de negocio.

05. El Proceso de Pruebas (Planificación ➡️ Diseño ➡️ Ejecución ➡️ Evaluación ➡️ Cierre)
• Ejemplo 1 (Fase de Diseño): El ingeniero de QA lee la documentación de una tienda en línea y redacta detalladamente un caso de prueba con pasos e instrucciones específicas: "Paso 1: Añadir artículo, Paso 2: Ir a checkout, Resultado esperado: Mostrar el botón de pagar activo".
• Ejemplo 2 (Fase de Evaluación): Al finalizar la semana de pruebas de una aplicación, el Líder de QA revisa los tableros de métricas para comparar la cantidad de errores descubiertos frente a los resueltos, determinando si el software es lo suficientemente estable como para autorizar su salida al mercado.

06. Ejercicios Propuestos y Resueltos (Casos de análisis de riesgo, selección de tipo de prueba y cálculo ROI)
• Ejemplo 1 (Análisis de Riesgo): En una aplicación médica, el módulo de "Alertas de ritmo cardíaco" se clasifica como de Riesgo Crítico Alto (puede costar vidas), mientras que el módulo de "Cambiar foto de perfil" es de Riesgo Bajo. Con esto resuelto, el equipo decide asignar el 80% de su tiempo disponible a probar el ritmo cardíaco.
• Ejemplo 2 (Cálculo del ROI de Automatización): Un ejercicio donde se calcula el Retorno de Inversión (ROI): Si ejecutar una prueba de regresión manual cuesta $500 cada mes, pero crear un script automatizado cuesta $2,000 una sola vez y se ejecutará durante los próximos dos años, el ejercicio demuestra matemáticamente que la automatización se paga sola a partir del cuarto mes.

TEMA 01
¿Por qué Probamos Software? [cite: 34]
📖
Definición

"Probar software es el proceso de evaluar un sistema o componente para verificar que satisface los requisitos especificados y para identificar diferencias entre resultados esperados y reales." — IEEE 829 [cite: 35, 36]

🛡️ Prevenir fallos [cite: 37, 38]

Encontrar defectos antes de que lleguen al usuario. Un bug en prod cuesta 100× más que en diseño[cite: 39].

💰 Reducir costos [cite: 40, 41]

El costo de corrección crece exponencialmente. Detectar temprano = ahorro real[cite: 42].

👤 Satisfacción usuario [cite: 43, 44]

Software que funciona genera confianza, lealtad y reputación de marca[cite: 45].

⚖️ Cumplimiento legal [cite: 46, 47]

Sectores como salud, finanzas y aviación EXIGEN pruebas certificadas por norma[cite: 48].

❌
Mitos vs. Realidad en las Pruebas [cite: 49]

MITO: "Las pruebas son pérdida de tiempo" [cite: 50, 51] → REALIDAD: IBM estima que por cada $1 invertido se ahorran $4 (ROI 4:1)[cite: 52, 53, 55].

MITO: "Si el código compila, funciona" [cite: 56, 57] → REALIDAD: El 95% de los bugs son lógicos, no sintácticos. El compilador nunca los detecta[cite: 58, 59, 60].

MITO: "El testing es solo al final" [cite: 61, 62] → REALIDAD: Un error en requisitos que llega a producción cuesta hasta 200× más corregirlo[cite: 63, 64, 65].

MITO: "Los testers ralentizan el desarrollo" [cite: 66, 67] → REALIDAD: Equipos con QA integrado desde el inicio entregan proyectos un 40% más rápido[cite: 68, 69, 70].

📝
Mis apuntes

• Prevenir Fallos: Consiste en descubrir y solucionar los defectos (bugs) en las etapas iniciales del desarrollo antes de que el producto llegue al usuario final. Es una medida crítica, ya que un error detectado en producción (cuando el sistema ya está en uso) puede costar hasta 100 veces más que si se hubiera detectado en la fase de diseño.
• Reducir Costos: Está directamente ligado a la detección temprana. El costo de corregir un error aumenta exponencialmente a medida que el software avanza en su ciclo de vida. Encontrar los problemas a tiempo se traduce en un ahorro real de dinero y tiempo para el equipo de desarrollo y la empresa.
• Satisfacción del Usuario: Un software que pasa por pruebas de calidad funciona de manera correcta, fluida y sin interrupciones para el cliente. Esto genera confianza, lealtad y una excelente reputación de marca, asegurando que los usuarios sigan utilizando el producto de forma positiva.
• Cumplimiento Legal: En ciertas industrias, las pruebas no son opcionales, sino un requisito obligatorio exigido por regulaciones y normativas gubernamentales o internacionales. Sectores críticos como la salud, las finanzas y la aviación exigen pruebas certificadas por norma para garantizar la seguridad de los datos y, en muchos casos, la vida de las personas.

TEMA 03
Los 7 Principios Fundamentales del Testing (ISTQB) [cite: 95]
📋
Principios
1

Muestran presencia de defectos: Revelan defectos pero NO prueban que esté 100% libre de ellos[cite: 97, 98].

2

Pruebas exhaustivas imposibles: Probar todas las combinaciones es inviable; se usa análisis de riesgo[cite: 100, 101].

3

Pruebas tempranas: El costo crece 10× por fase. Probar desde requisitos ahorra dinero[cite: 103, 104].

4

Agrupamiento de defectos: El 80% de defectos se concentra en el 20% del código (Pareto)[cite: 106, 107].

5

Paradoja del pesticida: Tests repetidos dejan de encontrar nuevos errores. Deben actualizarse[cite: 109, 110].

6

Dependen del contexto: Un sistema médico y un juego requieren estrategias distintas[cite: 112, 113].

7

Ausencia de errores es falacia: Un sistema sin bugs que no cumple las necesidades NO es calidad[cite: 115, 116].

📝
Mis apuntes

• EJEMPLOS: Principios de las Pruebas de Software (QA)
• Las pruebas muestran presencia de defectos: Demuestran la existencia de fallos, pero no que el sistema sea 100% perfecto. Ejemplo: Si pruebas un formulario con contraseñas incorrectas y todo funciona bien, mañana un usuario podría ingresar un carácter especial (como un emoji 🚀) que rompa el sistema porque esa combinación exacta jamás se evaluó.
• Las pruebas exhaustivas son imposibles: Es inviable probar todas las combinaciones posibles de datos. Ejemplo: En un campo de contraseña de 8 a 16 caracteres con símbolos y números, probar cada variante tomaría millones de años; por ello, el tester prioriza mediante análisis de riesgo evaluando solo los límites (ej. contraseñas de 7, 8, 16 y 17 caracteres).
• Pruebas tempranas ahorran tiempo y dinero: Encontrar fallos en etapas iniciales reduce el costo de corrección. Ejemplo: Corregir una ambigüedad sobre divisas en el documento de requisitos toma 5 minutos; descubrir ese mismo vacío legal con la app ya lanzada en producción en Europa costará miles de dólares y parches de emergencia.
• Agrupamiento de defectos (Regla de Pareto): El 80% de los fallos suele concentrarse en el 20% de los módulos debido a su complejidad. Ejemplo: En una app bancaria, el módulo de Transferencias Internacionales acumula casi todos los errores del sistema por sus conexiones externas y tasas en tiempo real, mientras que el perfil o el modo oscuro no fallan.
• La paradoja del pesticida: Si se corren las mismas pruebas una y otra vez, llegará un punto en que no encontrarán fallos nuevos. Ejemplo: Ejecutar la misma lista de 50 pruebas automatizadas por un año dará "0 errores" porque el código ya se adaptó a ellas, pero los nuevos bugs de las funciones recientes pasarán desapercibidos si no se actualiza el set de pruebas.
• Las pruebas dependen del contexto: La estrategia cambia según el tipo de software. Ejemplo: Un juego móvil casual se prueba buscando fluidez y consumo de batería, donde un bug visual es menor; en cambio, el software de un marcapasos o de un avión exige simulaciones matemáticas ultra rigurosas porque un solo fallo cuesta vidas.
• Ausencia de errores es una falacia: Que un sistema no tenga bugs no significa que sea exitoso si no cumple las expectativas del usuario. Ejemplo: Crear un software impecable y con cero fallos que gestiona inventarios mediante disquetes es un fracaso comercial si el mercado actual opera 100% en la nube y las computadoras ya no tienen lectores físicos.

Ejercicio 1: Cálculo del ROI de Pruebas [cite: 178]

Enunciado: 30 defectos en codificación. Costos: $80 (codificación), $400 (sistema), $2.000 (producción). QA cuesta $8.000/mes[cite: 180, 181, 182].

  • Ahorro Detección Temprana: En producción costarían $60.000. En código cuestan $2.400. Ahorro = $57.600 (25× más barato)[cite: 186, 187, 188, 189, 190].
  • Cálculo del ROI: (Ahorro $57.600 - QA $8.000) / $8.000 × 100 = 620%[cite: 193, 194, 195].
    Por cada $1 invertido se ahorraron $7.20[cite: 196].
📝
Mis apuntes

    • Casos de Estudio Financiero y ROI en QA
    • Ejercicio 1: App de Banca Móvil (Fintech)
      • Enunciado: Se detectan 25 defectos en codificación. Costos por bug: Codificación $100, Sistema $500, Producción $3,000. El equipo de testing costó $10,000 por 1 mes.
      • Ahorro por detección temprana: Costo codificación ($25 \times \$100 = \$2,500$) vs. Costo producción ($25 \times \$3,000 = \$75,000$). $\text{Ahorro} = \$75,000 - \$2,500 = \mathbf{\$72,500}$. Detectar los errores en codificación fue 30 veces más barato.
      • ROI de las pruebas: Con una inversión de $10,000 y un beneficio de $72,500, aplicando la fórmula $\text{ROI} = \frac{\text{Beneficio} - \text{Inversión}}{\text{Inversión}} \times 100$, el resultado es $\frac{72,500 - 10,000}{10,000} \times 100 = \mathbf{625\%}$. Significa que por cada $1 invertido, la empresa ahorró $7.25 en producción.
    • Ejercicio 2: Plataforma de Comercio Electrónico (E-commerce)
      • Enunciado: Se resuelven 40 defectos en desarrollo. Costos por bug: Codificación $50, Sistema $250, Producción $1,500. El ingeniero de QA y las herramientas costaron $5,000 por el mes.
      • Ahorro por detección temprana: Costo codificación ($40 \times \$50 = \$2,000$) vs. Costo producción ($40 \times \$1,500 = \$60,000$). $\text{Ahorro} = \$60,000 - \$2,000 = \mathbf{\$58,000}$. Se evitó una pérdida potencial logrando un ahorro neto de $58,000.
      • ROI de la estrategia: Con una inversión de $5,000 y un beneficio de $58,000, aplicando la fórmula de retorno, el resultado es $\frac{58,000 - 5,000}{5,000} \times 100 = \mathbf{1060\%}$. Es decir, por cada $1 invertido en QA automatizado, la empresa evitó gastar $11.60 en parches de emergencia.

Ejercicio 2: Selección del Tipo de Prueba [cite: 197]
  • A. Modificación módulo autenticación: Validar lo que ya funcionaba[cite: 200, 201]. Solución: Prueba de Regresión, verifica que cambios no rompen el sistema[cite: 202, 203].
  • B. Cliente valida requerimientos: Antes de aceptar el proyecto[cite: 205]. Solución: Prueba de Aceptación (UAT), define si es entregable[cite: 206, 207].
  • C. Verificar calcularDescuento(): Retorna 15%[cite: 209]. Solución: Prueba Unitaria, aislada y rápida[cite: 210, 211].
  • D. Soportar 10.000 usuarios concurrentes:[cite: 213]. Solución: Prueba de Carga/Estrés[cite: 214, 215].
📝
Mis apuntes

    • Tipos y Ejemplos de Pruebas de Software
    • A. Prueba de Regresión: Confirma que el código nuevo o modificaciones no hayan roto las funciones existentes del sistema. Ejemplo: Al añadir la función "Pagar con Apple Pay" en una app de comida, QA vuelve a verificar que procesos antiguos como "añadir al carrito", "aplicar cupones" o "cambiar dirección" sigan funcionando perfectamente.
    • B. Prueba de Aceptación (UAT): Evaluaciones finales realizadas por usuarios reales para validar que el sistema cumple con el contrato y las necesidades del negocio. Ejemplo: Médicos y recepcionistas usan un nuevo sistema de gestión clínica simulando flujos reales para validar que sea intuitivo y cumpla lo acordado antes de autorizar el lanzamiento.
    • C. Prueba Unitaria: Pruebas ultra rápidas ejecutadas por desarrolladores para verificar de forma aislada el comportamiento de una pequeña función de código. Ejemplo: Validar mediante una línea de código automática si la función esUsuarioPremium() devuelve correctamente True al recibir los datos de un usuario que pagó su suscripción.
    • D. Prueba de Carga / Estrés: Simulación de volumen masivo de tráfico para analizar el rendimiento del servidor ante una alta demanda o identificar su punto de quiebre. Ejemplo: Usar un software como JMeter para simular a 15,000 estudiantes virtuales inscribiéndose al mismo tiempo en la plataforma web de una universidad para ver si el sistema se ralentiza o se cae por completo.
