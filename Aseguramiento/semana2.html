TEMA 01
¿Qué es la Mejora Continua?
🌱
Concepto y Filosofía Kaizen

"La mejora continua es el proceso sistemático de identificar, analizar y mejorar los procesos de una organización de forma permanente, con el fin de optimizar el rendimiento y la calidad."

Filosofía Kaizen: Kai = Cambio · Zen = Bueno. Pequeñas mejoras constantes, involucrando a todo el equipo. Es una cultura, no un evento puntual.

🎯
¿Qué busca?
  • Eliminar desperdicios (waste)
  • Reducir defectos y reprocesos
  • Aumentar eficiencia y velocidad
  • Satisfacer al cliente de forma sostenida
💻
En Software
  • Mejorar la calidad del código
  • Optimizar pipelines CI/CD
  • Reducir deuda técnica
  • Aprender de cada iteración

TEMA 02
El Ciclo PDCA de Deming — Origen e Historia
📜
Historia del Ciclo PDCA
  • 1930s: Walter Shewhart propone el ciclo PDSA en los laboratorios Bell
  • 1950s: W. Edwards Deming lo populariza en Japón tras la II Guerra Mundial
  • 1960s: Kaoru Ishikawa lo integra en los círculos de calidad japoneses
  • 1980s: Occidente adopta el ciclo; ISO lo incorpora en sus normas
  • Hoy: Base de Scrum, DevOps, Lean y estándares ISO 9001/25010

"Si no puedes describir lo que haces como un proceso, no sabes lo que estás haciendo."
— W. Edwards Deming, estadístico y consultor, padre del movimiento de calidad moderno

🔄
Las 4 Fases del Ciclo PDCA
  • P — PLAN (Planificar): Identificar el problema o área a mejorar · Establecer objetivos medibles · Diseñar el plan de acción
  • D — DO (Hacer): Implementar el plan en escala piloto · Capacitar y ejecutar con el equipo · Documentar todo lo ocurrido
  • C — CHECK (Verificar): Medir y registrar resultados obtenidos · Comparar resultados vs objetivos · Identificar desviaciones y aprendizajes
  • A — ACT (Actuar): Estandarizar lo que funcionó · Escalar la solución a producción · Iniciar un nuevo ciclo PDCA

TEMA 03
PDCA Aplicado al Desarrollo de Software
💻
Fases aplicadas al software
  • PLAN: Definir requisitos y criterios de aceptación · Planificar sprints · Diseñar arquitectura · Estimación de esfuerzo.
    Herramientas: User Stories · Backlog · Diagrama de Gantt · Risk Matrix
  • DO: Codificación · Code reviews · Integración continua (CI) · Pruebas unitarias y de integración.
    Herramientas: Git · Jenkins · SonarQube · JUnit / Pytest · Docker
  • CHECK: Pruebas de regresión · Análisis de métricas · Revisión del sprint · Reportes de defectos.
    Herramientas: JIRA · TestRail · Coverage reports · Burndown charts · Dashboards QA
  • ACT: Retrospectivas · Refactoring · Actualizar estándares · Documentar lecciones aprendidas.
    Herramientas: Retrospective boards · Wikis · Playbooks · KPIs actualizados
🔄
PDCA en la Práctica — Scrum y DevOps

Scrum como implementación del PDCA:

  • PLAN → Sprint Planning: selección de backlog, objetivos del sprint
  • DO → Sprint (ejecución): Daily standups, desarrollo, integración
  • CHECK → Sprint Review: Demo al cliente, validación de incremento
  • ACT → Sprint Retrospective: Mejoras al proceso para el próximo sprint

DevOps y el Ciclo PDCA: Plan → Code & Build → Test & Monitor → Release & Operate → (nuevo ciclo)

TEMA 04
Herramientas, Métricas y Caso Práctico
📊
Caso Práctico — Sistema de Matrícula Estudiantil
  • PLAN — Problema detectado: El sistema falla al registrar más de 200 usuarios simultáneos. Objetivo: reducir errores de concurrencia un 90% antes del próximo período.
  • DO — Acciones implementadas: Se implementó un sistema de cola de peticiones · Pruebas de carga con JMeter · Refactoring del módulo de sesiones.
  • CHECK — Verificación: Pruebas con 300 usuarios simultáneos: tasa de error bajó de 34% a 2.1%. Métricas documentadas en el dashboard de QA.
  • ACT — Estandarización: El patrón de colas se adoptó en todos los módulos · Estándar de codificación actualizado · Nuevo ciclo: mejorar tiempo de respuesta.
📈
Métricas Clave para Medir la Mejora Continua
Métrica Meta Descripción
🐛 Defect Density < 1 bug / KLOC Defectos por miles de líneas de código
⏱️ Lead Time días / semanas Tiempo desde idea hasta producción
🔄 Change Failure Rate < 15% % despliegues que causan incidentes
🚀 Deployment Frequency diario / semanal Frecuencia de liberación de software
🔧 MTTR < 1 hora Mean Time To Recovery
📊 Cobertura de Pruebas > 80% % código cubierto por pruebas automatizadas
