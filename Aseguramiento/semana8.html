TEMA 01
¿Qué es una Prueba Unitaria?
💡
Definición y Principios FIRST

"Una prueba unitaria verifica el comportamiento de una UNIDAD de código (función, método o clase) de manera aislada, con entradas controladas y salidas verificables."

Letra Principio Descripción
F Fast (Rápidas) Se ejecutan en milisegundos. Miles de tests en segundos.
I Independent (Independientes) No dependen de otros tests ni de BD, red o archivos.
R Repeatable (Repetibles) Misma entrada → mismo resultado siempre, en cualquier entorno.
S Self-Validating (Autovalidables) Pass o Fail automático. Sin interpretación manual.
T Timely (Oportunas) Escritos al mismo tiempo o antes del código de producción.
🔍
¿Qué ES y qué NO ES una unidad?

✅ SÍ es una unidad:

  • Una función o método.
  • Una clase con su comportamiento.
  • Un módulo pequeño aislado.

❌ NO es una unidad:

  • Un flujo que llama a la BD.
  • Una integración entre módulos.
  • Código que accede a red/disco.

TEMA 02
Patrón AAA — Arrange, Act, Assert
🧩
Estructura Universal de un Test Unitario

A - ARRANGE (Preparar)

Configura todo lo que el test necesita: objetos, datos de entrada, mocks y condiciones iniciales.

// Arrange
double precio = 200.0;
double descuento = 0.15;
Calculadora calc = 
  new Calculadora();

💡 Solo datos necesarios. Nombres descriptivos.

A - ACT (Ejecutar)

Llama a la función o método que se está probando. Solo UNA llamada por test.

// Act
double resultado = 
  calc.aplicar(
    precio, 
    descuento);

💡 Una sola llamada. Sin lógica aquí.

A - ASSERT (Verificar)

Verifica que el resultado obtenido coincide con el esperado. El test falla aquí si hay un bug.

// Assert
assertEquals(
  170.0, 
  resultado, 
  0.001);

💡 Mensaje claro al fallar. (assertEquals / assertTrue).

TEMA 04
Herramientas — JUnit (Java) y PyTest (Python)

☕ JUnit 5 — Java

import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

class CalculadoraTest {
    @Test
    void testDescuento_precioValido() {
        // Arrange
        Calculadora calc = new Calculadora();
        // Act
        double res = calc.descuento(200, 0.15);
        // Assert
        assertEquals(170.0, res, 0.001);
    }

    @Test
    void testDescuento_precioNegativo() {
        assertThrows(IllegalArgException.class,
            () -> calc.descuento(-50, 0.10));
    }
}

🐍 PyTest — Python

import pytest
from calculadora import descuento

# Happy path
def test_descuento_precio_valido():
    # Arrange
    precio, pct = 200, 0.15
    # Act
    resultado = descuento(precio, pct)
    # Assert
    assert resultado == 170.0

# Boundary
def test_descuento_cero_pct():
    assert descuento(100, 0) == 100.0

# Exception
def test_precio_negativo_raises():
    with pytest.raises(ValueError):
        descuento(-50, 0.10)

TEMA 05
TDD y Cobertura de Código (Code Coverage)
🔄
TDD — Test Driven Development

🔴 Paso 1: RED

Escribe un test para la funcionalidad que AÚN NO EXISTE. El test debe fallar. Si no falla, algo está mal.

🟢 Paso 2: GREEN

Escribe el código de producción MÍNIMO necesario para que el test pase. Nada más, nada menos.

🔵 Paso 3: REFACTOR

Limpia el código: elimina duplicación, mejora nombres. Los tests deben seguir pasando.

Beneficios: Diseño más limpio, cobertura alta por defecto, detecta regresiones al instante, documentación viva y menos debugging.

📈
Cobertura de Código (Code Coverage)

Tipos de Cobertura

  • > 80% Líneas: % de líneas de código ejecutadas al menos una vez.
  • > 70% Ramas: % de ramas (if/else, switch) ejercitadas.
  • > 90% Funciones: % de funciones/métodos llamados.
  • > 65% Condiciones: % de booleanos evaluados como V y F.

🛠 Herramientas: JaCoCo (Java), Coverage.py (Python), Istanbul/NYC (JS)

Interpretación del Coverage

  • < 50% INSUFICIENTE: Alta probabilidad de bugs ocultos.
  • 50–70% BÁSICO: Cubre caminos principales, faltan bordes.
  • 70–85% ACEPTABLE: Buen balance. Estándar de industria.
  • 85–100% EXCELENTE: Alta confianza. Para sistemas críticos.

E2: Identificar AAA y Aplicar TDD

a) Identifique las secciones AAA en este test Java:

@Test
void testRegistroEstudiante() {
  String nombre = "Ana";
  int edad = 20;
  Registro reg = new Registro();
  boolean result = reg.registrar(nombre, edad);
  assertTrue(result);
  assertEquals("Ana", reg.getNombre());
}
  • ARRANGE: nombre, edad, Registro reg = new Registro()
  • ACT: reg.registrar(nombre, edad)
  • ASSERT: assertTrue(result), assertEquals("Ana", reg.getNombre())

b) Ordene los pasos del ciclo TDD:

  1. A - Escribir un test para la función sumarLista() que aún no existe
  2. B - Ejecutar el test → falla (rojo). Es el comportamiento esperado.
  3. C - Ejecutar todos los tests y confirmar que pasan (verde) [Nota: Previamente se escribe el código mínimo, luego sucede el C]
  4. D - Refactorizar: extraer constantes, mejorar nombres de variables
  5. E - Ejecutar tests → siguen en verde. Proceso completado.

✅ Orden correcto: A → B → C → D → E

E3: Análisis de Cobertura y Tests Faltantes

ENUNCIADO: La función clasificar_nota(nota) tiene 5 ramas (if/elif/else). Actual Coverage = 40%. Identifique qué casos faltan para 100%.

def clasificar_nota(nota):
  if nota < 0 or nota > 100: raise ValueError('Inválida')  # B1
  elif nota >= 90: return 'Sobresaliente'                 # B2
  elif nota >= 70: return 'Aprobado'                      # B3
  elif nota >= 51: return 'Recuperación'                  # B4
  else: return 'Reprobado'                                # B5
  • ✅ B1 (Error): Cubierto con nota=-1 y nota=101
  • ✅ B2 (Sobresaliente): Cubierto con nota=95
  • ❌ B3 (Aprobado): FALTA: test con nota=75
  • ❌ B4 (Recuperación): FALTA: test con nota=60
  • ❌ B5 (Reprobado): FALTA: test con nota=30

Conclusión: Se necesitan 3 tests adicionales (B3, B4, B5) para subir del 40% al 100% (todas ramas cubiertas).

Puntos clave
  • 01. Una prueba unitaria verifica UNA unidad aislada. Debe ser FIRST: rápida, independiente y automática. [cite: 324, 325]
