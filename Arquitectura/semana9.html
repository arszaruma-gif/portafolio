Arquitectura Cloud-Native — Diseñando para la Elasticidad, Resiliencia y Alta Disponibilidad Global

TEMA 01
¿Qué significa ser "Nativo de la Nube"?
☁️
Concepto

No se trata simplemente de tomar un sistema viejo y ejecutarlo en una máquina virtual de AWS u Azure (eso es Cloud-Hosted).

  • ☁️ Diseño Dedicado: Aplicaciones pensadas desde el primer día para explotar el modelo de computación en la nube.
  • ⚡ Ventajas Dinámicas: Escalado automático bajo demanda, tolerancia a fallos de infraestructura e implementación continua sin interrupciones.
📝
Mis apuntes

• Enfoque Tradicional o "Cloud-Hosted" (Alojado en la Nube)

📝 ENUNCIADO: Se analiza el comportamiento de una arquitectura de software heredada (monolito) cuando es migrada mediante una estrategia Lift-and-Shift hacia infraestructura virtualizada en proveedores de nube (AWS/Azure).

Criterio de Operación Comportamiento ante Alta Demanda Impacto en el Negocio / Limitación
Estrategia de Escalado Escalado vertical o réplicas de instancias completas. Es obligatorio duplicar todo el bloque del monolito. Lento y Costoso: Las máquinas virtuales idénticas tardan minutos en inicializarse y consumen presupuesto excesivo.
Tolerancia a Fallos Acoplamiento fuerte en un único proceso y base de datos centralizada. Punto Único de Fallo: Si un componente (ej. la base de datos) colapsa, toda la aplicación se cae para todos los usuarios.
# Representación conceptual de un despliegue Cloud-Hosted
infraestructura_virtual = {
    "instancia_aws_ec2": ["Autenticacion", "Buscador", "ReproductorVideo", "BaseDatosLocal"],
    "escalado": "Duplicar instancia gigante completa (Tarda varios minutos)"
}

• Enfoque "Cloud-Native" (Nativo de la Nube)

📝 ENUNCIADO: Se evalúa el desempeño de una arquitectura diseñada de forma nativa para la nube, distribuida en microservicios independientes dentro de contenedores (Docker) y gestionada dinámicamente por un orquestador (Kubernetes).

Ventaja Dinámica Mecanismo de Acción (Viernes por la noche) Resultado Técnico y Operativo
Escalado Horizontal Automático Ante saturación en la "Reproducción de video", el orquestador genera de forma aislada 20 copias del microservicio. Eficiencia Financiera: Los pods se levantan en segundos. Módulos como "Perfil de usuario" mantienen su consumo intacto.
Aislamiento y Tolerancia a Fallos Un error crítico de código rompe o detiene el contenedor del módulo de "Recomendaciones". Degradación Aceptable: El usuario deja de ver sugerencias, pero sigue reproduciendo su video. El sistema no sufre un apagón total.
Implementación Continua (CI/CD) Se realiza el despliegue y actualización del componente "Buscador" directamente en hora pico de tráfico. Cero Downtime: Los usuarios siguen navegando sin interrupciones y se elimina el cartel de "En mantenimiento".
# Representación conceptual de una topología Cloud-Native
arquitectura_kubernetes = {
    "pod_auth": {"replicas": 1, "estado": "estable"},
    "pod_buscador": {"replicas": 1, "estado": "actualizando_sin_caidas"},
    "pod_reproductor": {"replicas": 20, "estado": "escalado_automatico_segundos"},
    "pod_recomendaciones": {"replicas": 0, "estado": "error_aislado_no_afecta_al_resto"}
}
📜
Definición según la CNCF

"Las tecnologías nativas de la nube empoderan a las organizaciones para construir y ejecutar aplicaciones escalables en entornos modernos y dinámicos como nubes públicas, privadas e híbridas."

🏛️
Los Cuatro Pilares Cloud-Native

📦 Contenedores

Aislamiento estándar y ligero (Docker) que empaqueta la aplicación con todas sus dependencias garantizando que funcione igual en cualquier entorno.

🧩 Microservicios

Sistemas divididos en componentes autónomos y débilmente acoplados que agilizan el despliegue y minimizan el impacto de fallos.

♾️ CI/CD automatizado

Automatización total desde la compilación y pruebas hasta la entrega, permitiendo subir a producción múltiples veces al día de forma segura.

⚙️ DevOps y Herramientas Declarativas

Enfoque cultural y tecnológico que unifica el desarrollo y las operaciones mediante configuraciones que describen el estado deseado del sistema.

Evidencias

• 1. Contenedores (Aislamiento y Eficiencia)

📝 CONTEXTO: Tecnología de empaquetado que encapsula una aplicación junto con sus dependencias, permitiendo su ejecución aislada sobre un único sistema operativo compartido.

Capacidad Clave Mecanismo Operativo Impacto / Beneficio Directo
Portabilidad Absoluta Empaqueta el binario, dependencias y variables en una imagen inmutable e idéntica. Elimina el clásico conflicto operativo de "en mi máquina sí funcionaba".
Eficiencia de Recursos Comparte el núcleo (kernel) del S.O. anfitrión sin necesidad de emular un sistema completo. Alta densidad: Más aplicaciones ejecutándose con menor consumo de RAM y CPU.
Consistencia de Entornos Mantiene configuraciones rígidas desde desarrollo hasta producción. Mitiga fallos colaterales por disparidad de versiones de software.
# Manifiesto conceptual de un contenedor (Docker de ejemplo)
contenedor_app = {
    "base": "alpine-linux-shared-kernel",
    "dependencias": ["python3.11", "libs_sistema"],
    "ejecucion": "Garantizada idéntica en Local, Staging y Producción"
}

• 2. Microservicios (Desacoplamiento Funcional)

📝 CONTEXTO: Estilo arquitectónico que divide un sistema de software en un conjunto de servicios autónomos, modulares y altamente enfocados en un dominio de negocio.

Capacidad Clave Mecanismo Operativo Impacto / Beneficio Directo
Escalabilidad Granular Replica únicamente el componente de alta demanda (ej. Carrito de Compras) de forma independiente. Optimización financiera extrema al no duplicar todo el sistema.
Tolerancia a Fallos Aislada Aísla los procesos de cada microservicio mediante fronteras de red claras (APIs/Mensajería). Si un servicio colapsa, los demás continúan operando con normalidad.
Flexibilidad Tecnológica Desvincula el stack tecnológico global, asignando contratos independientes entre equipos. Permite usar el lenguaje o base de datos óptima para cada tarea específica.
# Topología de microservicios distribuidos e independientes
servicios_autonomos = {
    "ms_carrito": {"lenguaje": "Go", "base_datos": "Redis", "escalas": 5},
    "ms_usuarios": {"lenguaje": "Node.js", "base_datos": "PostgreSQL", "escalas": 1},
    "ms_notificaciones": {"estado": "caído", "efecto": "no_afecta_a_los_demás_servicios"}
}

• 3. CI/CD Automatizado (Integración y Entrega Continuas)

📝 CONTEXTO: Flujos automatizados (pipelines) encargados de compilar, probar y desplegar los cambios de código de manera ágil y segura.

Capacidad Clave Mecanismo Operativo Impacto / Beneficio Directo
Velocidad de Lanzamiento Automatiza de manera integral las suites de compilación, empaquetado y ejecución de pruebas. Despliegue de actualizaciones, parches y mejoras múltiples veces al día.
Reducción de Error Humano Sustituye por completo los procesos, configuraciones e inicios de sesión manuales en servidores externos. Mitiga de raíz distracciones o configuraciones accidentales hechas a mano.
Feedback Inmediato Ejecuta pruebas unitarias e integrales inmediatamente tras cada confirmación de cambios (git push). Notifica errores en minutos, permitiendo corregirlos antes de afectar a producción.
# Ejecución secuencial del pipeline automatizado
pipeline_cicd = ["1. Build Imagen", "2. Run PyTest (Falla -> Cancela / Pasa -> Sigue)", "3. Deploy Automático"]

• 4. DevOps y Herramientas Declarativas (Cultura e Infraestructura)

📝 CONTEXTO: Convergencia de prácticas culturales, filosofías de trabajo colaborativo y automatización para gestionar la infraestructura como código modificable.

Capacidad Clave Mecanismo Operativo Impacto / Beneficio Directo
Infraestructura como Código (IaC) Define topologías de red, servidores y bases de datos mediante archivos descriptivos de texto. Reconstrucción e instanciación idéntica de la infraestructura en minutos por script.
Colaboración Unificada Sincroniza y fusiona las metas de los desarrolladores (Dev) con las del equipo de operaciones (Ops). Alineación en estabilidad del sistema, velocidad de entrega y monitoreo.
Auditoría y Control Almacena los archivos declarativos del sistema dentro de repositorios de versiones (ej. Git). Trazabilidad histórica completa y posibilidad de realizar rollback inmediato.
# Archivo de configuración declarativa (Estado Deseado)
manifiesto_infraestructura = {
    "tipo": "Infraestructura_Como_Codigo_IaC",
    "redes": ["subred-privada-vpc-1", "balanceador-carga-http"],
    "historial_versiones": "Controlado en Git (Sencillo auditar o revertir cambios)"
}
TEMA 02
Patrones de Resiliencia Distribuidos — Asumiendo que en la nube todo va a fallar en algún momento
🔌
El Patrón Circuit Breaker (Disyuntor)

Evita que el fallo de un servicio de terceros o interno sature en cascada a todo el ecosistema de la aplicación.

  • 🟢 Closed (Cerrado): El flujo opera con normalidad. Las peticiones pasan sin problema.
  • 🔴 Open (Abierto): Se detectan demasiados errores concurrentes. El circuito intercepta las llamadas de inmediato devolviendo un fallo rápido o data en caché (Fallback).
  • 🟡 Half-Open (Semi-Abierto): Deja pasar una cantidad mínima de tráfico de prueba para validar si el servicio remoto se recuperó.

Mis apuntes

• 1. Máquinas Virtuales (VMs) — Aislamiento a Nivel de Hardware

📝 CONTEXTO: Entornos de ejecución independientes que emulan un hardware físico completo mediante un hipervisor, cargando un Sistema Operativo (SO) invitado completo para cada instancia.

Perspectiva Mecanismo Técnico y Operativo Impacto en la Infraestructura
Ventaja Aislamiento robusto (Hardware): Separadas estrictamente por el hipervisor. Si una instancia colapsa o se infecta, el daño queda confinado. Alta seguridad perimetral y blindaje del servidor físico anfitrión.
Ventaja Flexibilidad de SO: Cada VM empaqueta su propio núcleo. Permite cohabitar instancias de Windows y Linux en el mismo hardware. Idóneo para ejecutar software heredado con dependencias nativas del sistema operativo.
Desventaja Consumo masivo: El almacenamiento se mide en Gigabytes (GB) al arrastrar archivos de sistema redundantes de un SO completo. Saturación acelerada del almacenamiento físico en disco.
Desventaja Lentitud de arranque: El proceso de inicialización requiere minutos al cargar servicios y controladores desde cero. Poca agilidad operativa ante picos repentinos de tráfico de usuarios.
Desventaja Asignación estática: Recursos prefijados (ej. reservar 8 GB de RAM bloquea los recursos aunque solo se consuma 1 GB). Desperdicio presupuestario y baja eficiencia del hardware disponible.
# Representación conceptual de una Máquina Virtual (VM)
maquina_virtual = {
    "capa_aislamiento": "Hipervisor (Hardware dedicado)",
    "sistema_operativo": "SO Invitado Completo (Kernel Propio)",
    "peso_promedio": "Gigabytes (GB)",
    "recursos": "Asignación estática rígida (Baja elasticidad)"
}

• 2. Contenedores (Docker) — Virtualización a Nivel de Sistema Operativo

📝 CONTEXTO: Paquetes de software ligeros y portables que comparten el núcleo (Kernel) del sistema operativo anfitrión, aislando únicamente los binarios y dependencias de la aplicación.

Perspectiva Mecanismo Técnico y Operativo Impacto en la Infraestructura
Ventaja Ligereza extrema: El tamaño se cuantifica en Megabytes (MB). Contienen exclusivamente el código y las librerías del servicio. Almacenamiento ultra optimizado y transferencia veloz por red.
Ventaja Arranque instantáneo: Inicio en milisegundos o pocos segundos al no requerir booteo de un sistema operativo. Alta velocidad para escalar horizontalmente de forma reactiva ante tráfico masivo.
Ventaja Uso elástico: Consumo dinámico sobre el kernel compartido; solo absorbe RAM y CPU a demanda real. Máxima densidad: Permite consolidar muchos más servicios por servidor.
Desventaja Menor aislamiento (SO): Si un agente malicioso explota una vulnerabilidad y compromete el Kernel compartido, afecta al nodo entero. Requiere políticas de seguridad (SecOps) e imágenes base depuradas.
Desventaja Dependencia del Kernel base: La aplicación debe ser compatible con la arquitectura del sistema operativo hospedador. No es posible correr binarios nativos de Windows directo en un Kernel Linux sin capas de traducción.
# Representación conceptual de un Contenedor (Docker)
contenedor_docker = {
    "capa_aislamiento": "Espacios de nombres / Cgroups (Nivel SO)",
    "sistema_operativo": "Ninguno (Comparte el Kernel del Anfitrión)",
    "peso_promedio": "Megabytes (MB)",
    "recursos": "Uso elástico dinámico (Alta eficiencia corporativa)"
}
💡 Criterio de Selección Estratégica: Seleccione Máquinas Virtuales cuando el requerimiento principal involucre aislamiento total por normativas de seguridad estricta o disparidad crítica de Sistemas Operativos. Seleccione Contenedores cuando requiera optimización de costos, velocidad de despliegue, flexibilidad y arquitecturas de microservicios modernas.

TEMA 03
Orquestación con Kubernetes (K8s) — El estándar de facto para la gobernanza de contenedores a escala
⚙️
¿Qué resuelve Kubernetes en Producción?

Gestionar manualmente cientos de contenedores Docker individuales es inviable. K8s automatiza el ciclo de vida.

  • 🩹 Self-Healing: Si un contenedor muere, K8s lo levanta de nuevo en milisegundos de forma automática.
  • 📈 Horizontal Scaling: Sube o baja el número de réplicas en función del tráfico del servidor.
  • 🔍 Service Discovery: Balancea la carga nativamente entre las réplicas del contenedor.
📋
La Metodología de los 12-Factor Apps

Un manifiesto de buenas prácticas críticas para asegurar la portabilidad y limpieza de aplicaciones en la nube. Destacamos tres factores clave:

III. Configuraciones

Estricta separación: Almacena las variables de entorno, credenciales y llaves de bases de datos completamente fuera del código fuente.

VI. Procesos

Stateless (Sin estado): La aplicación debe ejecutarse como uno o más procesos que no guardan nada local en disco. Todo lo persistente va a servicios externos.

XI. Logs

Flujo continuo: Trata los logs de la app como flujos de eventos de salida continuos sin preocuparte por guardarlos en archivos internos.

Mis apuntes

• Ventajas de usar Kubernetes (Orquestación Inteligente)

📝 CONTEXTO: Plataforma de código abierto para la automatización, el despliegue, el escalado y la gestión de aplicaciones contenedorizadas en clústeres de cómputo.

Capacidad Nativa Mecanismo Técnico y Operativo Impacto / Beneficio Directo
Autoreparación
(Self-Healing)		 Monitorea continuamente el estado de salud de los pods. Reinicia o reemplaza instancias corruptas de inmediato. Máxima disponibilidad; el cliente final no percibe la falla del contenedor.
Escalado Horizontal
Elástico		 Ajusta de manera automática el número de réplicas de los contenedores basándose en métricas de consumo de CPU/RAM. Eficiencia de costos al eliminar el aprovisionamiento de recursos ociosos.
Enrutamiento y
Balanceo de Carga		 Asigna direccionamiento IP propio y nombres DNS únicos a los contenedores, distribuyendo el tráfico equitativamente. Previene la saturación de pods individuales y simplifica el Service Discovery.
Cero Inactividad
(Zero-Downtime)		 Ejecuta actualizaciones progresivas (Rolling Updates). Ejecuta un Rollback automático inmediato si detecta anomalías. Despliegues seguros en producción sin interrumpir el servicio.
# Estado Deseado gestionado por el plano de control (Control Plane)
estado_clúster_k8s = {

• Desventajas de usar Kubernetes (Complejidad y Desafíos Operativos)

📝 CONTEXTO: Exigencias infraestructurales, técnicas y cognitivas requeridas para la implementación y el mantenimiento continuo de la plataforma.

Factor Crítico Mecanismo Técnico y Operativo Impacto en la Infraestructura
Curva de Aprendizaje Demanda el dominio profundo de redes abstractas, almacenamiento persistente distribuidor y definición declarativa en YAML. Necesidad estricta de ingenieros especializados (DevOps / SRE).
Sobrecarga Psicológica
y Técnica (Overkill)		 Aplicaciones de baja complejidad son forzadas a adoptar topologías de red clúster redundantes. Desperdicio de tiempo, esfuerzo y presupuesto en proyectos pequeños.
Configuración Inicial Requiere el diseño manual de políticas de seguridad (RBAC), mallas de red y aprovisionamiento de volúmenes persistentes. Fase inicial compleja y susceptible a errores humanos latentes.
Costo de Gestión Los componentes del Control Plane (etcd, API server, scheduler) consumen hardware solo para coordinar los nodos. Mantenimiento costoso y actualizaciones de versión rigurosas.

Los alumnos tomarán la API de matrículas desarrollada en las clases previas y construirán una imagen optimizada multi-etapa utilizando un Dockerfile.

Objetivo: Pasar variables de base de datos usando variables de entorno nativas externas.

WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt

Criterios de Validación Técnica
  • 🔁 Inmutabilidad: La imagen creada debe poder ejecutarse idénticamente tanto de forma local como simulando la nube.
  • 📦 Optimización de Peso: Uso correcto de imágenes base ligeras (-slim o alpine) para reducir la superficie de ataque y tiempos de red.
  • 🔒 Seguridad Básica: Configuración del contenedor para que se ejecute bajo un usuario sin privilegios (Non-root user).

📂 config/database.py 
import os

class Settings:
    # Captura variables nativas del contenedor o asigna un default
    DB_HOST: str = os.getenv("DB_HOST", "localhost_default")
    DB_USER: str = os.getenv("DB_USER", "root")
    DB_NAME: str = os.getenv("DB_NAME", "matriculas_db")

settings = Settings()
📂 app/main.py 
from fastapi import FastAPI
from config.database import settings

app = FastAPI(title="Microservicio de Matrículas")

@app.get("/")
def inicio():
    return {
        "mensaje": "API de Matrículas Operativa (Estructura Limpia)",
        "infraestructura_cloud": {
            "base_de_datos_host": settings.DB_HOST,
            "usuario_db": settings.DB_USER,
            "nombre_db": settings.DB_NAME
        }
    }

Compilación optimizada mediante Multi-Stage Builds para reducir el tamaño final de la imagen:

# --- ETAPA 1: Constructor (Builder) ---
FROM python:3.11-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

# --- ETAPA 2: Imagen Final Ejecutable ---
FROM python:3.11-slim AS final
WORKDIR /app

# Copia dependencias aisladas desde la etapa builder
COPY --from=builder /root/.local /root/.local
COPY ./config ./config
COPY ./app ./app

ENV PATH=/root/.local/bin:$PATH
ENV PYTHONPATH=/app
EXPOSE 8000

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Comandos para construir y ejecutar el contenedor inyectando variables dinámicamente:

# 1. Construir la imagen optimizada
docker build -t api-matriculas .

# 2. Levantar el contenedor inyectando credenciales de prueba
docker run -d -p 8000:8000 \
  -e DB_HOST="produccion-yavirac-db" \
  -e DB_USER="admin_matriculas" \
  -e DB_NAME="yavirac_db" \
  --name app-matriculas api-matriculas
