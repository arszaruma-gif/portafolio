TEMA 01
¿Qué son los Patrones de Diseño?
🎯
Concepto — Gang of Four (GoF)

Introducidos por la Gang of Four (GoF), son soluciones estándar a problemas comunes en el diseño de software orientado a objetos.

  • 🔤 Lenguaje Común: Permiten a los desarrolladores comunicarse con términos técnicos claros (ej. "Usa un Adapter").
  • ♻️ Reutilización: Evitan reinventar la rueda ante problemas de diseño recurrentes.
📂
Categorías de la GoF
  • 🏗️ 1. Creacionales: Mecanismos de creación de objetos. (Esta semana)
  • 🔗 2. Estructurales: Composición de clases y objetos. (Esta semana)
  • 🔄 3. Comportamiento: Interacción y responsabilidades entre objetos. (Semana 7)

💡 "Los patrones no son fragmentos de código para copiar; son plantillas conceptuales para resolver problemas de diseño."

TEMA 02
Patrones Creacionales — Abstraen el proceso de instanciación de objetos
🏗️
El Catálogo Creacional Completo

📦 Singleton

Garantiza que una clase tenga una única instancia en todo el sistema y proporciona un punto de acceso global.

🏭 Factory Method

Define una interfaz para crear un objeto, pero deja que las subclases decidan qué clase exacta instanciar.

🏗️ Abstract Factory

Permite producir familias de objetos relacionados o dependientes sin especificar sus clases concretas.

🔨 Builder

Separa la construcción de un objeto complejo de su representación, permitiendo crear variaciones paso a paso.

📋 Prototype

Permite copiar u clonar objetos existentes sin que el código dependa de sus clases específicas.

💻
Patrón en Acción: Singleton — Conexión a Base de Datos

Problema: Múltiples instancias abiertas saturan los recursos del servidor.

Solución: Controlar el constructor internamente para garantizar una sola instancia.

class DatabaseConnection:
  _instance = None

  def __new__(cls):
    if cls._instance is None:
      cls._instance = super().__new__(cls)
      # Inicializar conexión aquí
    return cls._instance

TEMA 03
Patrones Estructurales — Cómo se entrelazan los objetos para formar estructuras más grandes
🔗
El Catálogo Estructural (1/2)

🔌 Adapter

Permite que clases con interfaces incompatibles trabajen juntas, traduciendo las peticiones de una a otra.

🌉 Bridge

Separa una abstracción de su implementación, permitiendo que ambas varíen y crezcan de forma independiente.

🌳 Composite

Compone objetos en estructuras de árbol para representar jerarquías parte-todo, tratando objetos individuales y composiciones por igual.

🔗
El Catálogo Estructural (2/2)

✨ Decorator

Añade responsabilidades a un objeto de forma dinámica sin alterar su estructura interna ni usar herencia.

🏛️ Facade

Proporciona una interfaz simplificada y unificada para un subsistema complejo de clases, ocultando la complejidad técnica.

🪶 Flyweight

Optimiza el uso de memoria compartiendo eficientemente estados comunes entre grandes cantidades de objetos similares.

🔒 Proxy

Proporciona un sustituto o intermediario para controlar el acceso a otro objeto (ej. control de permisos, caché o carga perezosa).

💻
Patrón en Acción: Adapter — Integración de APIs

Esencial cuando integramos servicios de terceros (Gateways de pago, APIs de mapas) que cambian con frecuencia sus firmas.

  • Problema: El API externo usa un método pay_usd(), pero nuestra arquitectura espera procesar_cobro().
  • Solución: El Adapter envuelve el API viejo y expone el formato nuevo.

El Reto: Adapter XML → JSON

Dada una clase vieja que exporta listas de estudiantes en formato XML estructurado, los alumnos deberán implementar un Adapter para entregar la misma data en formato JSON plano.

Objetivo: No alterar la clase original que genera el XML.

Criterios de Evaluación:

  • ✅ Correcta separación de responsabilidades.
  • ✅ Uso de tipos nativos de Python para la conversión.
  • ✅ Pruebas que demuestren que el cliente interactúa únicamente con la interfaz del Adapter.
