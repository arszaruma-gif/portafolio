TEMA 01
¿Qué es la Arquitectura de Software?
🎯
Concepto

Imagina que vas a construir un edificio. La "programación" es poner los ladrillos y el cemento. Pero la "Arquitectura" es decidir si ese edificio será un hospital, una discoteca o una casa.

  • Si es un hospital, necesitas que la electricidad nunca falle (Disponibilidad).
  • Si es una discoteca, necesitas que el suelo aguante a mil personas saltando (Escalabilidad).
  • Si es una casa, quizás lo más importante sea que sea barata y acogedora (Costo / Mantenibilidad).

En Software: La arquitectura es el conjunto de decisiones que son difíciles de cambiar después. No se trata de qué colores usar, sino de cómo se comportará el sistema bajo presión.

TEMA 02
El Gran Dilema: El "Trade-off" (Sacrificios)
⚖️
Concepto

Un arquitecto de software es un negociador. No existe el software perfecto que sea:

  • Infinitamente rápido.
  • 100% seguro.
  • Totalmente gratis.
  • Muy fácil de programar.

Regla de oro: Para ganar algo, siempre hay que sacrificar otra cosa.

📊
Ejemplo práctico

Caso: Quieres que el sistema de notas sea ultra seguro con reconocimiento facial y doble factor de autenticación (2FA).

Sacrificio: Los alumnos tardarán más en entrar (pérdida de Velocidad/Usabilidad) y el instituto gastará más dinero en servidores (pérdida de Costo).

TEMA 04
Disponibilidad (Availability)
📊
Concepto y métricas — Los "nueves"

Es la métrica que indica qué porcentaje del tiempo un sistema está "vivo" y respondiendo a los usuarios.

  • 99% (Dos nueves): Puede estar caído hasta 3.6 días al año.
  • 99.9% (Tres nueves): Solo puede fallar 8.7 horas al año.
  • 99.999% (Cinco nueves): El estándar de oro. Solo puede fallar 5 minutos al año.
🔧
¿Cómo se logra la alta disponibilidad?

La clave es eliminar los Puntos Únicos de Fallo (SPOF):

  • Redundancia: Tener copias de todo. Si un servidor se quema, hay otro listo para tomar su lugar inmediatamente.
  • Balanceadores de Carga (Load Balancers): Reparte a los usuarios entre servidores sanos. Si uno falla, el balanceador deja de enviarle tráfico.
📝
Mis apuntes

¿De qué depende la disponibilidad? Para que tu software sea altamente disponible, no basta con que el código esté bien escrito; entran en juego varios factores: Fiabilidad (Reliability): Que el sistema no falle. Si falla poco, es más fácil que esté disponible. Recuperación (Resilience): Qué tan rápido vuelve a levantarse el sistema después de un error. Redundancia: Tener "copias" del sistema. Si un servidor se quema, otro entra en acción de inmediato (como el ejemplo de la RAM que mencionaste: si tienes varios módulos y uno falla, el sistema podría seguir si está diseñado para ello). Mantenimiento: La capacidad de actualizar la app sin tener que apagarla (el famoso "estamos en mantenimiento" reduce la disponibilidad).

TEMA 05
Escalabilidad (Scalability)
📈
Concepto

Es la capacidad de un sistema para manejar una carga creciente de trabajo (más usuarios, más datos, más transacciones) añadiendo recursos, sin que el sistema se rompa o se vuelva lento.

⚖️
Vertical vs Horizontal

A. Escalabilidad Vertical (Scaling Up)

Añadir más potencia al servidor que ya tienes (más RAM, procesador más rápido, disco SSD).

  • ✅ Ventaja: Fácil, no requiere cambiar el código.
  • ⚠️ Desventaja: Tiene límite físico, es caro. Si falla, todo se apaga.

B. Escalabilidad Horizontal (Scaling Out)

Añadir más servidores en lugar de hacer uno más grande. Como contratar 10 camiones pequeños en lugar de un camión gigante.

  • ✅ Ventaja: Prácticamente infinita. Miles de servidores pequeños trabajando juntos.
  • ⚠️ Desventaja: Requiere software diseñado para trabajo distribuido (Microservicios).

TEMA 06
Resiliencia: "Saber caerse y levantarse"
🥊
Concepto — La Analogía del Boxeador

La resiliencia no es evitar fallos (eso es imposible), sino la capacidad de recuperarse de un fallo y seguir funcionando.

Un boxeador no es resiliente porque nunca recibe un golpe. Es resiliente porque cuando lo mandan a la lona, se levanta antes de que la cuenta llegue a diez y sigue peleando.

💻
Aplicación en Software

Imagina que tu app necesita consultar el precio del dólar en una API externa:

  • ❌ Sistema NO resiliente: La API se cae → pantalla blanca, app muerta.
  • ✅ Sistema Resiliente: La API se cae → usa el último precio guardado y avisa: "Precio de hace 5 minutos". La app sigue viva.
🔧
Estrategias Técnicas (Patrones)
  • Circuit Breaker (Disyuntor): Si un servicio falla mucho, el sistema "abre el circuito" y deja de llamarlo temporalmente para no colapsar.
  • Retry (Reintento): Si una petición falla por un problema de red momentáneo, el sistema lo intenta automáticamente 2 o 3 veces.

TEMA 07
Fiabilidad (Reliability)
🎯
Concepto y diferencia con Disponibilidad

Es la probabilidad de que un sistema realice sus funciones sin errores, durante un período determinado. Si el usuario presiona un botón 100 veces, las 100 veces debe hacer exactamente lo que se espera.

🏦 Disponibilidad: "La puerta del banco está abierta."
✅ Fiabilidad: "Entro, pido mi saldo y el valor que me dan es el correcto."

🏗️
Los tres pilares de la Fiabilidad

A. Errores de Hardware

El disco duro puede quemarse aunque el software esté perfecto. Solución: Redundancia.

B. Errores de Software

Bugs, fugas de memoria, excepciones no manejadas. Solución: Unit Testing, monitoreo y aislamiento de procesos.

C. Errores Humanos

Mala configuración o borrar tablas por accidente. Solución: Interfaces que hagan difícil cometer errores y fácil recuperarse de ellos (botones de "Deshacer").

📏
¿Cómo medimos la Fiabilidad? MTBF y MTTR
  • MTBF (Mean Time Between Failures): Tiempo promedio entre fallos. Queremos que sea muy alto.
  • MTTR (Mean Time To Repair): Tiempo promedio de reparación. Queremos que sea muy bajo.
🏫
Ejemplo Práctico — Sistema de Calificaciones YAVIRAC
  • ❌ No Fiable: El profesor ingresa 9.5, hay un error de red y el sistema guarda 0.0. Estuvo disponible, pero falló en fiabilidad.
  • ✅ Fiable: El sistema detecta el error, reintenta, verifica que el dato llegó íntegro y confirma: "Dato guardado correctamente".

TEMA 08
Durabilidad: "Que el dato y el sistema perduren"
🪨
Durabilidad de Datos — El Grabado en Piedra

Es la garantía de que, una vez que el sistema confirma que guardó algo, esa información no se perderá, incluso si hay un incendio en el servidor.

Si escribes en una pizarra y se moja, se borra. Si lo grabas en piedra, aunque llueva, el mensaje sigue ahí. La durabilidad es ese "grabado en piedra".

Cuando haces una transferencia y la app dice "Éxito", el sistema debe asegurar que ese dato se escribió y se replicó. Si el servidor explota un segundo después, el dinero no puede desaparecer.

⏳
Durabilidad Arquitectónica (Longevidad del código)

Es qué tan bien envejece tu código. Un software con alta durabilidad puede seguir funcionando y actualizarse 5 o 10 años después sin tener que borrarlo todo y empezar de cero.

Actividad 1 — Cajero Automático

Pregunta: ¿Qué es peor: que el cajero esté apagado (Baja Disponibilidad) o que te dé $20 pero te descuente $200 (Baja Fiabilidad)?

Mi respuesta:

• Escenario A: El cajero está apagado (Baja Disponibilidad)
• El impacto: Es muy molesto. Tienes que caminar tres cuadras, buscar otro cajero o regresar más tarde.
• El estado del sistema: El sistema falló en dar el servicio, pero protegió la información. Tu dinero sigue intacto en el banco.
• Costo de reparación: Relativamente bajo. Se reinicia el sistema, se cambia la pieza dañada y listo.

• Escenario B: El cajero te roba dinero (Baja Fiabilidad)
• El impacto: Es una catástrofe absoluta. El usuario pierde dinero, entra en pánico y la empresa destruye por completo la confianza de sus clientes (y se gana una demanda legal).
• El estado del sistema: El sistema está "disponible" (te atendió), pero sus datos y su lógica están corruptos.
• Costo de reparación: Altísimo. Arreglar esto implica auditorías manuales, revisar bases de datos descuadradas, hacer devoluciones y lidiar con un caos de soporte técnico.

✅
Actividad 2 — App de Mensajería tipo WhatsApp

Pregunta: ¿Qué es peor en un banco: que la app no abra por 5 minutos (Falla de Resiliencia) o que se pierda el registro de un depósito de $500 (Falla de Durabilidad)?

Mi respuesta:

• 1. Si falla la Resiliencia
• El escenario: El usuario intenta enviar un mensaje, hay un micro-corte de internet y la app se cierra sola o se queda congelada.
• El resultado: Mala experiencia.
• Lección de arquitectura: La resiliencia es la capacidad de un sistema para soportar y recuperarse de fallos parciales. Un diseño resiliente incluiría lógica de reintentos o manejo de errores para que la app no colapse ante un problema de red.

• 2. Si falla la Durabilidad
• El escenario: El usuario envía el mensaje, la app dice "Enviado", pero el servidor se reinicia y el mensaje se borra de la base de datos. El receptor nunca lo lee.
• El resultado: Pérdida de información crítica.
• Lección de arquitectura: La durabilidad garantiza que, una vez que se le confirma al usuario que una acción se completó, los datos se mantienen grabados permanentemente, incluso si el hardware o el software fallan inmediatamente después.
