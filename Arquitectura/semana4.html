TEMA 01
El Cambio de Paradigma a Microservicios
🌐
De Monolitos a Ecosistemas Distribuidos

Se experimenta una transición desde los sistemas monolíticos tradicionales, donde absolutamente todo "vive" y se ejecuta dentro de un único proceso, hacia ecosistemas fragmentados que tienen la obligación de colaborar e interactuar de forma constante sobre la red[cite: 2].

Anatomía de los Microservicios

  • Descomposición Funcional: Cada servicio se enfoca de forma estricta en un único dominio de negocio (denominado Bounded Context)[cite: 2]. Esto reduce el radio de explosión ante posibles fallos y permite realizar un escalado selectivo del software[cite: 2].
  • Despliegue Independiente: Permite que equipos de ingeniería autónomos suban a producción actualizaciones del servicio de "Pagos" sin la necesidad de esperar al equipo a cargo de "Catálogo", acelerando drásticamente el Time-to-Market[cite: 2].

⚠️ Visualizando la Escala: Cuando los servicios crecen de forma exponencial, la comunicación se vuelve el problema principal[cite: 2]. El Service Mesh emerge como la solución definitiva para gestionar adecuadamente el tráfico de la red[cite: 2].

TEMA 02
Gestión de Datos: Saga vs 2PC
📊
Estrategias de Transaccionalidad

Garantizar la integridad de los datos a través de múltiples servicios independientes requiere abandonar las transacciones ACID convencionales[cite: 2].

Característica 2-Phase Commit (2PC)[cite: 2] Patrón SAGA[cite: 2]
Consistencia Fuerte (Atómica)[cite: 2] Eventual[cite: 2]
Bloqueo Sí (Bloquea recursos)[cite: 2] No (Optimista)[cite: 2]
Escalabilidad Baja (Cuello de botella)[cite: 2] Alta (Asíncrona)[cite: 2]
Fallo Rollback automático[cite: 2] Transacción Compensatoria[cite: 2]

Checklist imperativo de Datos Distribuidos

  • Database-per-service: Nunca compartas una base de datos común entre microservicios; incurre en acoplamiento oculto[cite: 2].
  • API Composition: Une y mezcla datos de múltiples servicios en la capa del API Gateway para servirlos al frontend[cite: 2].
  • CQRS: Separa de forma estricta la lógica de escritura (comandos) de la lógica de lectura (consultas) para optimizar altas cargas[cite: 2].
  • Idempotencia: Asegura técnicamente que procesar el mismo mensaje de red dos veces no altere el estado final del sistema[cite: 2].
📝
Mis apuntes

Tabla Comparativa

Criterio 2PC (Two-Phase Commit) Patrón Saga

Tipo de Consistencia

ACID (Estricta): Los datos son idénticos en todos los servicios en el mismo milisegundo.

Eventual: El sistema puede estar en un estado "gris" temporalmente hasta que se estabilice.

Bloqueo de Recursos

Sí: Bloquea las bases de datos de todos los servicios involucrados hasta que termina la transacción.

No: Cada servicio guarda sus datos inmediatamente, liberando recursos para otros usuarios.

Protocolo de Comunicación

Típicamente Síncrono (RPC, gRPC o llamadas HTTP directas).

Típicamente Asíncrono (Basado en eventos con Kafka, RabbitMQ, etc.).

Punto Único de Fallo

Alto: Si el Coordinador Central se cae a mitad del proceso, el sistema queda en un limbo indeterminado.

Bajo: Al ser distribuido (especialmente en coreografía), no depende de un único servidor crítico.

Manejo de Errores

Rollback Automático: La base de datos deshace el cambio como si nunca hubiera pasado.

Acciones Compensatorias: Hay que escribir código explícito para "revertir" la acción (ej. depositar dinero de vuelta, cancelar reservas de hotel, etc.).

Impacto en el Rendimiento

Malo en alta demanda: A mayor número de microservicios, más lento se vuelve el sistema por la espera de confirmaciones.

Excelente: Permite procesar millones de transacciones por segundo porque nadie espera a nadie de forma síncrona.

TEMA 03
El Concepto y los Pilares de Observabilidad
👁️
Entender el Interior desde el Exterior

La observabilidad no es sinónimo de simple monitoreo[cite: 2]. Se define formalmente como la capacidad técnica de entender y deducir el estado interno de un sistema distribuido basándose únicamente en sus salidas externas[cite: 2]. Responde eficientemente a tres preguntas clave:

  • Detección: ¿Qué servicio o componente está fallando?[cite: 2]
  • Aislamiento: ¿En dónde exacto se localiza el cuello de botella?[cite: 2]
  • Diagnóstico: ¿Por qué ocurrió específicamente el error en producción?[cite: 2]
📐
Los Tres Pilares de la Observabilidad (M.E.L.T)

Para recuperar el control en arquitecturas distribuidas, nos apoyamos de forma estricta en tres pilares esenciales[cite: 2]:

  1. Logs (Registros): Bloques inmutables de eventos discretos en el tiempo[cite: 2]. Nos proveen la certeza del "cuándo" y el "qué" sucedió con sumo detalle[cite: 2].
  2. Métricas: Valores numéricos agregados calculados sobre el tiempo[cite: 2]. Muestran tendencias claras de salud: uso de CPU, Memoria, tasas de error y Latencia[cite: 2].
  3. Traces (Trazas): El mapa de ciclo de vida completo de una petición HTTP/RPC a través de múltiples microservicios[cite: 2]. Es la herramienta vital para hallar latencias ocultas[cite: 2].
📝
Mis apuntes

• Los más comunes en Desarrollo Web y Software
• A11y (Accessibility / Accesibilidad): Se usa para todo lo relacionado con diseñar software accesible para personas con discapacidades (lectores de pantalla, contrastes altos, etc.). Hay 11 letras entre la 'A' y la 'y'.
• I18n (Internationalization / Internacionalización): Es el proceso de diseñar el código de una aplicación para que pueda adaptarse a diferentes idiomas y regiones sin necesidad de reescribirlo. Tiene 18 letras en medio.
• L10n (Localization / Localización): A diferencia de la internacionalización, este es el proceso real de traducir y adaptar el software a un país específico (cambiar monedas, formatos de fecha, modismos).
• C14n (Canonicalization / Canonicalización): En bases de datos y SEO, es el proceso de convertir datos que tienen múltiples formatos posibles a un único formato estándar o "canónico".

🖼️
Evidencias de la Suite de Observabilidad

• Métricas (Metrics)
• Las métricas son datos numéricos agregados medidos a lo largo del tiempo.
• Son los signos vitales de tu software.

• ¿Qué está pasando y qué tan grave es?
• Ejemplos: El uso de CPU está al 92%, la base de datos está recibiendo 5,000 peticiones por segundo, o el porcentaje de errores 500 subió al 4%.
• Su valor: Son extremadamente ligeras y baratas de almacenar. Sirven para activar las alertas (por ejemplo, que te llegue un mensaje a Slack si el sistema se ralentiza). No te dicen exactamente cuál es el error, pero te avisan que hay un incendio.

• Registros (Logs)
• Un log es una línea de texto que describe un evento específico que ocurrió en un momento exacto.
• Es el diario de navegación de tu código.

• ¿Por qué está pasando esto?
• Ejemplo: [2026-06-03 10:14:22] ERROR - ServicioPagos: Error de conexión con el banco. Tarjeta rechazada para el usuario ID: 99482.
• Su valor: Es el nivel máximo de detalle. Cuando la métrica te avisa que hay errores, vas a los logs para ver la descripción exacta del fallo o el stack trace del código.
• El problema: Almacenar trillones de líneas de texto de miles de microservicios se vuelve muy costoso y difícil de buscar si no están centralizados.

• Trazas (Traces / Distributed Tracing)
• Una traza representa el viaje completo de una petición desde que el usuario hace clic en la aplicación hasta que pasa por todos los microservicios fragmentados y responde.

• ¿Dónde se está rompiendo o ralentizando el flujo?
• Ejemplo: El usuario le da a "Comprar". La traza te muestra gráficamente:
• Frontend tarda 10ms.
• Servicio de Autenticación tarda 15ms.
• Servicio de Inventario tarda 4.5 segundos (¡Aquí está el cuello de botella!).
• Su valor: En un sistema fragmentado, una sola petición puede tocar 10 servidores distintos. La traza le asigna un ID único a esa petición para que puedas ver cómo saltó de un servicio a otro y dónde se perdió el tiempo o se generó el error.

TEMA 04
Ecosistema Tecnológico y Objetivos de Rendimiento
🛠️
Herramientas Líderes del Mercado

El mercado ha estandarizado herramientas específicas para atacar cada uno de los pilares de manera óptima[cite: 2]:

  • Kibana / ELK Stack: Especializado en la ingesta masiva y agregación inteligente de Logs[cite: 2].
  • Prometheus: Motor de series temporales enfocado en la recolección de Métricas y disparo de Alertas operativas[cite: 2].
  • Jaeger: Framework open-source diseñado para habilitar el rastreo distribuido (*Distributed Tracing*)[cite: 2].
📈
Métricas de Rendimiento Reales (SLA y Percentiles)

En el mundo real de los sistemas distribuidos, no medimos el rendimiento utilizando promedios matemáticos simples, ya que estos ocultan las malas experiencias de usuario[cite: 2].

  • Disponibilidad (SLA): Fijado comúnmente en objetivos de alta disponibilidad como el $$99.9\%$$[cite: 2].
  • Latencia P99 (Percentil 99): Asegura de forma estadística que incluso el usuario que experimenta la mayor lentitud en la red obtenga una respuesta sub-200ms[cite: 2].

LABORATORIO
Laboratorio Práctico: Python + Prometheus Client
🚀
Reto de Instrumentación de la API de Pagos

Enunciado: Implementar instrumentación mediante código utilizando la librería prometheus_client para exponer métricas en tiempo real de una API de Pagos, enfocándonos en medir la latencia de validación con el banco externo[cite: 2].

Concepto Clave: Counter vs Histogram[cite: 2]

El Counter (Contador) incrementa de forma continua registrando únicamente el número total acumulado de pagos procesados[cite: 2]; el Histogram (Histograma) guarda de forma segregada cuánto tiempo toma cada petición individual, vital para calcular la latencia media y percentiles[cite: 2].

Código de la Práctica (Instrumentación):

from prometheus_client import start_http_server, Counter, Histogram
import time
import random

# Inicialización de métricas de Observabilidad
PAGOS_TOTALES = Counter('pagos_procesados_total', 'Número total de pagos')
LATENCIA_BANCO = Histogram('pago_validacion_banco_segundos', 'Tiempo de validación')

def procesar_pago():
    PAGOS_TOTALES.inc() # Incrementa el Contador
    
    with LATENCIA_BANCO.time(): # Mide de forma automática el tiempo de ejecución
        tiempo_simulado = random.uniform(0.05, 0.4)
        time.sleep(tiempo_simulado)

if __name__ == '__main__':
    # Servidor expuesto para que Prometheus haga scraping en el puerto 8000
    start_http_server(8000)
    print("Métricas expuestas en http://localhost:8000")
    while True:
        procesar_pago()
        time.sleep(1)

Conclusión General
"La distribución añade complejidad inherente, pero la observabilidad nos devuelve por completo el control."[cite: 2]

  • 🔄 Las arquitecturas SAGA entregan alta escalabilidad asíncrona mediante lógica compensatoria ante fallos[cite: 2].
  • 📊 Los promedios ocultan cuellos de botella; la métrica reina para asegurar calidad de servicio al usuario es la Latencia P99[cite: 2].
