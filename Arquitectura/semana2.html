TEMA 02
Documentación para Justificar Decisiones Arquitectónicas
⚠️
El problema sin documentación

El equipo cambia, el contexto se pierde. ¿Por qué usamos esta base de datos? ¿Por qué ese patrón? Nadie lo recuerda.

📋
Los tres pilares de la documentación
  • 📝 QUÉ — Describe la decisión tomada de forma clara y accionable
  • 🤔 POR QUÉ — Captura el razonamiento, las alternativas y las restricciones del momento
  • ⚖️ CONSECUENCIAS — Documenta trade-offs, deuda técnica y compromisos futuros

"Code tells you HOW. Comments tell you WHAT. Documentation tells you WHY." — D. Thomas

TEMA 03
Architecture Decision Records (ADRs)
🏗️
Estructura de un ADR
  • 1. Título — Nombre corto de la decisión (ej: "Usar PostgreSQL como BD principal")
  • 2. Estado — Propuesto / Aceptado / Obsoleto / Reemplazado
  • 3. Contexto — Situación y fuerzas que llevaron a tomar la decisión
  • 4. Decisión — Lo que se decidió y cómo se implementará
  • 5. Consecuencias — Positivas, negativas y compromisos resultantes (trade-offs)
📄
Plantilla Estándar de un ADR

# ADR-001: Usar arquitectura de microservicios para el módulo de pagos

## Estado: Aceptado

## Contexto: El módulo de pagos requiere escalabilidad independiente y distintos SLAs respecto al resto del sistema.

## Decisión: Extraer el módulo de pagos como microservicio independiente con su propia BD y API REST.

## Alternativas consideradas: Monolito modular (descartado: acoplamiento alto) · GraphQL gateway (descartado: complejidad innecesaria)

## Consecuencias:
✅ Escalado independiente   ✅ Despliegue autónomo
⚠️ Latencia de red adicional   ⚠️ Mayor complejidad ops

Ejercicio Resuelto 1 — Redacción de ADR (JWT)

Enunciado: El equipo eligió usar JWT para autenticación stateless en lugar de sesiones en servidor, para permitir escalar horizontalmente la API.

Título: ADR-002: Usar JWT para autenticación stateless

Estado: Aceptado

Contexto: La API debe escalar horizontalmente. Las sesiones en servidor crean estado compartido que dificulta el escalado.

Decisión: Usar JSON Web Tokens (JWT) firmados con RS256. Los tokens incluyen claims de identidad y expiran en 1h.

Consecuencias:
✅ Escalado horizontal sin sesiones compartidas   ✅ Stateless
⚠️ Imposibilidad de revocar tokens antes de expirar   ⚠️ Payload expuesto en base64

✅
Ejercicio Resuelto 2 — Análisis de ADR incompleto

ADR incompleto analizado:

Título: Base de datos  |  Estado: Aceptado  |  Decisión: MongoDB

[sin contexto] [sin consecuencias] [sin alternativas]

Problemas identificados:

  • ❌ Título genérico — no especifica la decisión real
  • ❌ Falta el Contexto — ¿qué problema se resolvía?
  • ❌ Decisión sin justificación — solo nombra la tecnología
  • ❌ No hay Alternativas evaluadas
  • ❌ No hay Consecuencias ni trade-offs documentados

💡 Un ADR debe capturar el CONTEXTO y las CONSECUENCIAS — sin ellos pierde su valor principal.

Ejercicio Propuesto 1 — Redacción de ADR (e-commerce)

Escenario: Eres arquitecto en una startup de e-commerce. Debes decidir entre arquitectura basada en eventos (Kafka/RabbitMQ) o llamadas REST síncronas para comunicar el servicio de órdenes con el de inventario. La startup tiene 3 devs, bajo presupuesto y debe salir a producción en 2 meses.

  • a) Identifica las fuerzas (contexto) que influyen en la decisión (mínimo 4)
  • b) Elige una opción y justifica tu elección
  • c) Documenta la decisión completa en formato ADR
  • d) Indica al menos 2 consecuencias positivas y 2 negativas
  • e) ¿Cuándo debería revisarse o reemplazarse este ADR?

Mi respuesta:

• Identificación de las Fuerzas (Contexto)
• Restricción de Tiempo Extrema (Time-to-Market): Salir a producción en 2 meses deja margen cero para curvas de aprendizaje complejas o depuración de infraestructura persistente.
• Capacidad del Equipo Muy Limitada: Un equipo de 3 desarrolladores debe enfocarse en la lógica de negocio (vender, cobrar, entregar). Operar y mantener clústeres de mensajería restaría ancho de banda crítico.
• Presupuesto Reducido: Minimizar el gasto en infraestructura inicial es vital. Levantarse en arquitecturas de eventos gestionadas o mantener servidores robustos para RabbitMQ eleva los costos fijos mensuales.
• Consistencia de Datos en E-commerce: En un flujo de compra, la consistencia entre la orden y el inventario es crítica para evitar la sobreventa (overselling).

• b) Elección y Justificación
• Decisión: Elegir Llamadas REST Síncronas (HTTP) entre el Servicio de Órdenes y el Servicio de Inventario.
• Justificación: En una startup en etapa temprana, la velocidad de entrega y la simplicidad superan a la arquitectura ideal. REST es un estándar dominado por el equipo, eliminando la curva de aprendizaje de patrones asíncronos. Además, permite validar el stock de forma inmediata dentro de la misma transacción de la orden.

• c) Documentación en formato ADR
• ADR 003: Comunicación Síncrona REST para los Servicios de Órdenes e Inventario.
• Estatus: Aprobado.
• Fecha: 8 de junio de 2026.
• Autor: Arquitecto de Software Principal / Startup E-commerce.
• Contexto: La startup necesita lanzar su MVP de comercio electrónico en un plazo estricto de 2 meses. El equipo está compuesto por 3 desarrolladores full-stack y el presupuesto es limitado.
• Decisión: Implementar comunicación síncrona mediante llamadas REST (HTTP/JSON) desde el Servicio de Órdenes hacia el Servicio de Inventario.
• Se descarta el uso de arquitecturas dirigidas por eventos (Kafka/RabbitMQ) en esta primera etapa.

• Justificación del ADR
• Time-to-Market: Desarrollar endpoints HTTP y clientes REST toma horas, mientras que implementar sistemas de mensajería tomaría semanas.
• Simplicidad Operativa: No es necesario aprovisionar, pagar ni monitorear brokers de mensajería.
• Consistencia Inmediata: Si el inventario responde con un error por falta de stock, la orden se cancela inmediatamente evitando la sobreventa.

• d) Consecuencias Positivas y Negativas
• Consecuencias Positivas:
    • Reducción drástica del tiempo de desarrollo.
    • Costos de infraestructura mínimos ($0 adicionales).
• Consecuencias Negativas:
    • Acoplamiento fuerte y disponibilidad ligada entre servicios.
    • Problemas de escalabilidad futura ante picos de tráfico.

• e) ¿Cuándo debería revisarse o reemplazarse este ADR?
• Hito de Tráfico/Escala: Cuando la plataforma supere de forma sostenida las 50 órdenes por minuto.
• Crecimiento del Equipo: Cuando el equipo pase de 3 a más de 8-10 desarrolladores.
• Adición de Nuevos Consumidores de Eventos: Cuando otros servicios necesiten reaccionar a la creación de órdenes y las llamadas REST síncronas se vuelvan difíciles de mantener. En ese momento, migrar a RabbitMQ o Kafka estará plenamente justificado.

Ejercicio Propuesto 2 — Mejora de ADR (React frontend)

ADR a mejorar: Título: Usar React · Estado: Aceptado · Contexto: El equipo sabe React · Decisión: Usaremos React · Consecuencias: Positivo: rápido de implementar.

  • a) Lista todos los problemas de calidad (mínimo 5)
  • b) Reescribe el ADR completo mejorando TODAS las secciones
  • c) Agrega sección de Alternativas Consideradas (mínimo 2)
  • d) ¿Sirve este ADR para un PM no técnico? ¿Por qué?

Mi respuesta:

• Problemas de Calidad Identificados (Mínimo 5)
• Falta de Contexto de Negocio y Técnico: Decir "el equipo sabe React" es una razón de conveniencia, no una justificación de arquitectura. No menciona qué se va a construir ni las restricciones del proyecto.
• Razonamiento Circular / Tautológico: El título es "Usar React" y la decisión es "Usaremos React". No existe un análisis real ni un proceso de diseño.
• Ausencia de Alternativas Consideradas: No se comparó React con Vue, Angular, Svelte o Vanilla JS, por lo que no se demuestra que sea la mejor opción.
• Consecuencias Superficiales e Incompletas: Solo menciona ventajas e ignora riesgos como SEO, mantenimiento de dependencias o tamaño del bundle.
• Falta de Detalles de Implementación: No se especifica si se utilizará Vite, Next.js, Redux, Zustand o Context API.
• Falta de Criterios de Revisión: No define cuándo la decisión debe ser reevaluada o reemplazada.

• b) y c) ADR 004 Mejorado (Incluye Alternativas)
• ADR 004: Selección de la Tecnología Frontend para la Aplicación del Cliente.
• Estatus: Aprobado.
• Fecha: 8 de junio de 2026.
• Autor: Equipo de Arquitectura y Core Frontend.

• Contexto
• Desarrollo de una nueva plataforma orientada al cliente.
• Requiere una interfaz altamente interactiva y actualizaciones de datos en tiempo real.
• El negocio exige un Time-to-Market de 3 meses para la versión Beta.
• El equipo está compuesto por 4 ingenieros con experiencia previa en JavaScript moderno.

• Alternativas Consideradas
• Alternativa 1: Vue.js (v3).
    • Pros: Curva de aprendizaje amigable y excelente rendimiento.
    • Contras: El equipo requiere capacitación adicional, afectando la fecha de entrega.

• Alternativa 2: HTML/Vanilla JS tradicional (Server-Rendered).
    • Pros: Excelente SEO y velocidad de carga inicial.
    • Contras: El mantenimiento de interfaces complejas es más difícil y propenso a errores.

• Decisión
• Adoptar React (v19+) junto con Vite como base de la arquitectura Frontend.
• No se utilizarán frameworks SSR como Next.js durante la primera etapa.
• La aplicación será una SPA (Single Page Application) alojada en un CDN para reducir la complejidad de infraestructura.

• Justificación
• Velocidad de Entrega: Todo el equipo domina React, permitiendo iniciar el desarrollo inmediatamente.
• Ecosistema y Madurez: Librerías como TailwindCSS, Shadcn, React Hook Form y Zustand aceleran el desarrollo y reducen trabajo adicional.

• Consecuencias Positivas (Ventajas)
• Alta velocidad de desarrollo inicial gracias a la reutilización de componentes.
• Facilidad para contratar nuevos desarrolladores debido a la popularidad de React en el mercado laboral.

• Consecuencias Negativas (Desventajas / Riesgos)
• SEO Deficiente: Al ser una SPA, el posicionamiento en buscadores puede verse afectado.
• Fatiga de JavaScript: La dependencia de múltiples librerías externas incrementa la deuda técnica y el mantenimiento.

• Criterios de Revisión
• La decisión deberá reevaluarse si el negocio requiere SEO orgánico estricto.
• En ese escenario, se considerará migrar a un framework con SSR como Next.js o Remix.

• d) ¿Sirve este ADR para un PM no técnico? ¿Por qué?
• Sí, la versión mejorada resulta útil para un Product Manager no técnico.
• Permite comprender claramente los beneficios y riesgos de la decisión tecnológica.
• Justifica el uso del tiempo y los recursos del equipo.
• Explica el impacto de la tecnología elegida sobre objetivos de negocio como Time-to-Market, SEO y contratación futura.
• Facilita la alineación entre las decisiones técnicas y las metas estratégicas del producto.

Ejercicio Propuesto 4 — Cadena de ADRs (Streaming)

Desarrolla una cadena de ADRs interrelacionados para un sistema de streaming de video:

  • ADR-001: Almacenamiento de videos — ¿S3, CDN propio o filesystem distribuido?
  • ADR-002: Protocolo de streaming — ¿HLS, DASH o RTMP? (referencia ADR-001)
  • ADR-003: Estrategia de caché — ¿Redis, Varnish o CDN edge? (referencia ADR-001 y 002)
  • ADR-004: Usuarios concurrentes — ¿WebSockets, SSE o polling? (referencia toda la cadena)

Mi respuesta:

```html

• ADR-001: Selección del Almacenamiento Base para Archivos de Video Master
• Estatus: Aprobado.
• Fecha: 8 de junio de 2026.
• Autor: Equipo de Arquitectura de Plataforma.

• Contexto
• El sistema de streaming necesita almacenar petabytes de archivos de video de alta definición.
• Se requiere alta durabilidad, disponibilidad, bajo costo por gigabyte e integración con herramientas de procesamiento y transcodificación.

• Alternativas Consideradas
• AWS S3 (Object Storage): Alta durabilidad, bajo costo y administración simplificada.
• CDN Propio On-Premise: Control total del hardware, pero costos operativos elevados.
• Filesystem Distribuido (GlusterFS/Ceph): Escalable, pero complejo de administrar.

• Decisión
• Utilizar AWS S3 como almacenamiento base y persistente para todos los recursos de video.

• Justificación
• Elimina la carga operativa de administrar discos y sistemas distribuidos.
• Permite automatizar políticas de ciclo de vida y almacenamiento frío.
• Facilita la integración con servicios de procesamiento en la nube.

• Consecuencias
• Positivas: Durabilidad extrema y escalabilidad automática.
• Negativas: Altos costos de egress, por lo que el acceso directo de clientes a S3 estará prohibido.

• ADR-002: Selección del Protocolo de Streaming para Distribución
• Estatus: Aprobado.
• Referencia: ADR-001.

• Alternativas Consideradas
• HLS (HTTP Live Streaming).
• DASH (Dynamic Adaptive Streaming over HTTP).
• RTMP (Real-Time Messaging Protocol).

• Decisión
• Adoptar HLS utilizando fragmentos fMP4 como protocolo principal de entrega.

• Justificación
• Compatible con la mayoría de dispositivos.
• Funciona sobre HTTP estándar.
• Se integra perfectamente con los archivos almacenados en S3.

• Consecuencias
• Positivas: Compatibilidad universal y aprovechamiento de tecnologías web existentes.
• Negativas: Latencia de entre 6 y 30 segundos, poco adecuada para interactividad en tiempo real.

• ADR-003: Diseño de la Estrategia de Caché y Red de Distribución (CDN)
• Estatus: Aprobado.
• Referencias: ADR-001 y ADR-002.

• Alternativas Consideradas
• CDN Global (Cloudflare, CloudFront, Akamai).
• Clúster de Reverse Proxies (Nginx/Varnish).
• Redis en Clúster.

• Decisión
• Implementar un CDN en el Edge frente al origen en AWS S3.

• Justificación
• Reduce drásticamente el tráfico directo hacia S3.
• Disminuye los costos de transferencia.
• Mejora significativamente la experiencia del usuario.

• Consecuencias
• Positivas: Escalabilidad global y soporte para millones de usuarios simultáneos.
• Negativas: Necesidad de gestionar cuidadosamente la invalidación de caché y los TTL de los manifiestos.

• ADR-004: Comunicación para Métricas en Tiempo Real y Usuarios Concurrentes
• Estatus: Aprobado.
• Referencias: ADR-001, ADR-002 y ADR-003.

• Alternativas Consideradas
• WebSockets.
• Server-Sent Events (SSE).
• Short Polling / Long Polling.

• Decisión
• Utilizar Server-Sent Events (SSE) para actualizaciones del servidor al cliente.
• Utilizar HTTP POST para el envío de métricas de telemetría desde el cliente.

• Justificación
• Mantiene una arquitectura basada en HTTP estándar.
• Reduce el consumo de memoria frente a WebSockets.
• Permite aprovechar HTTP/2 y HTTP/3 con reconexión automática.

• Consecuencias
• Positivas: Infraestructura más simple, escalable y alineada con la arquitectura de streaming existente.
• Negativas: Si se requieren funciones altamente interactivas en tiempo real, será necesario incorporar WebSockets o WebRTC en el futuro.

```

Mis apuntes sobre los ejercicios propuestos

EJEMPLOS DE EJERCICIO 1 - Fuerzas (Contexto)
• Título: Identificación de fuerzas restrictivas en la startup.
• Estado: Completado.
• Contexto:
• Tiempo de comercialización (Time-to-Market) crítico: el plazo límite de 2 meses exige priorizar soluciones de rápida implementación.
• Capacidad limitada del equipo: con solo 3 desarrolladores, no existe suficiente personal para mantener arquitecturas complejas.
• Presupuesto ajustado: no existe capital para costear infraestructura administrada como AWS MSK o servidores adicionales para mensajería.
• Curva de aprendizaje: implementar eventos requiere dominar patrones como consistencia eventual, colas de error e idempotencia, consumiendo tiempo valioso de desarrollo.

• Elección y Justificación
• Título: Selección del mecanismo de comunicación interservicio.
• Estado: Decidido.
• Contexto: Se debe elegir entre una arquitectura basada en eventos (Kafka/RabbitMQ) o llamadas REST síncronas para el flujo entre Órdenes e Inventario.
• Decisión: Utilizar llamadas REST síncronas.
• Justificación: En la etapa de MVP la prioridad es validar el negocio rápidamente. REST evita la sobreingeniería, reduce la complejidad y permite salir a producción en el tiempo establecido.

• ADR-001: Comunicación Síncrona entre Servicio de Órdenes e Inventario
• Estado: Aceptado.
• Contexto: El equipo de tres desarrolladores necesita verificar y descontar inventario cuando un cliente realiza una compra, con un plazo de dos meses y presupuesto reducido.
• Decisión: Utilizar llamadas HTTP/REST síncronas entre el Servicio de Órdenes y el Servicio de Inventario.
• El Servicio de Órdenes enviará una petición HTTP y esperará una respuesta (200 OK o 400 Error) antes de confirmar la compra.

• Justificación
• Reduce el tiempo necesario para implementar la comunicación entre servicios.
• No requiere instalar ni administrar un broker de mensajería.
• El equipo ya domina REST, evitando una curva de aprendizaje adicional.
• Permite entregar el Producto Mínimo Viable dentro del plazo establecido.

• Consecuencias
• Positivas:
• Implementación rápida.
• Infraestructura sencilla.
• Menor costo operativo.
• Desarrollo y depuración más simples.
• Negativas:
• Existe acoplamiento temporal entre los servicios.
• Si el servicio de Inventario falla, el servicio de Órdenes también fallará.
• Bajo alta demanda las peticiones pueden bloquear recursos y disminuir el rendimiento.

• Circunstancias Futuras de Revisión
• Título: Criterios de obsolescencia y migración del ADR.
• Estado: Monitoreado.
• El ADR será revisado cuando aparezcan nuevos servicios que deban reaccionar a una compra (Facturación, Envíos, Notificaciones, etc.).
• También será revisado cuando aumente significativamente el tráfico de usuarios y las conexiones HTTP comiencen a saturarse.
• La decisión podrá reemplazarse cuando el equipo crezca y sea necesario desacoplar completamente los servicios mediante una arquitectura basada en eventos.

• EJERCICIO 2 - Lista de Problemas de Calidad del ADR Original
• Título: Auditoría de calidad y deficiencias del ADR simplificado.
• Estado: Completado.
• Contexto: Se analiza el ADR original para identificar por qué no cumple con los estándares profesionales de documentación arquitectónica.

• Problemas Identificados
• Contexto extremadamente vago: "El equipo sabe React" no explica las necesidades del negocio ni las restricciones del proyecto.
• Falta de profundidad en la decisión: no especifica versiones, frameworks complementarios ni manejo del estado de la aplicación.
• Sesgo de confirmación: la decisión se basa únicamente en la experiencia del equipo sin evaluar criterios técnicos.
• Consecuencias incompletas: solo menciona beneficios y omite riesgos, costos y deuda técnica.
• No se documentan alternativas como Angular o Vue ni las razones para descartarlas.

• Consecuencias
• La falta de información reduce el valor histórico del ADR.
• Los futuros desarrolladores no comprenderán el motivo real de la decisión.
• Se dificulta el mantenimiento y la evolución de la arquitectura del sistema.

• ADR-003: Selección de React y Vite para el Frontend del Portal Educativo
• Estado: Aceptado.
• Contexto: El proyecto consiste en desarrollar un portal web educativo para gestionar cursos en línea con una interfaz dinámica y actualizaciones en tiempo real.
• El plazo de entrega es de tres meses y el equipo posee experiencia consolidada en React y JavaScript.

• Decisión
• Utilizar React versión 18 junto con Vite para el desarrollo del frontend.
• Emplear Zustand para la administración del estado global debido a su simplicidad y bajo consumo de recursos.

• Justificación
• React permite iniciar el desarrollo inmediatamente gracias a la experiencia del equipo.
• Vite proporciona tiempos de compilación y recarga muy rápidos.
• Zustand evita la complejidad innecesaria de Redux y facilita el mantenimiento del proyecto.

• Consecuencias
• Positivas: desarrollo más rápido, mejor rendimiento durante la programación y menor curva de aprendizaje.
• Negativas: React es una biblioteca y requiere seleccionar herramientas adicionales para el enrutamiento, organización del proyecto y componentes de interfaz.

• Alternativas Consideradas
• Angular: descartado por su elevada curva de aprendizaje y la falta de experiencia del equipo en TypeScript avanzado.
• Vue.js: considerado por su facilidad de uso, pero descartado porque el equipo ya domina React y su ecosistema ofrece una mayor cantidad de librerías disponibles.

• Conclusión de las Alternativas
• React fue seleccionado tras comparar sus ventajas frente a Angular y Vue.
• La decisión se fundamenta en un análisis técnico, el tiempo disponible y la experiencia del equipo de desarrollo.

• Evaluación para un Product Manager (PM) No Técnico
• Estado: Evaluado.
• El ADR original no resulta útil para un PM porque únicamente indica que el equipo conoce React.
• No explica cómo la decisión impacta en el presupuesto, el tiempo de entrega ni los riesgos del proyecto.

• Conclusión
• El ADR mejorado comunica claramente las razones de negocio y técnicas de la decisión.
• Permite comprender el impacto en costos, tiempos y mantenimiento del proyecto.
• Facilita la comunicación entre desarrolladores, arquitectos y responsables del negocio.

• EJERCICIO 3 - Consecuencias de la Falta de ADRs Históricos
• Título: Análisis de impacto por ausencia de documentación histórica.
• Estado: Evaluado.
• Contexto: El equipo de TechBank analiza la migración de un sistema bancario monolítico hacia una arquitectura de microservicios sin contar con registros históricos de las decisiones arquitectónicas originales.

• Consecuencias Identificadas
• Riesgo de romper reglas de negocio críticas al desconocer por qué ciertos módulos fueron diseñados de forma acoplada.
• Parálisis por análisis debido a discusiones constantes sobre decisiones del pasado.
• Repetición de errores previamente solucionados por no existir documentación histórica.
• Incremento de costos y riesgos técnicos durante el proceso de modernización.

• ADR-000: Selección de Arquitectura Monolítica para el Sistema Core de TechBank
• Estado: Superado (Histórico).
• Contexto: En 2011 TechBank necesitaba desarrollar su sistema bancario central con un equipo reducido, presupuesto limitado y tecnologías distribuidas aún poco maduras.
• Se requería una alta consistencia transaccional mediante una única base de datos relacional Oracle.

• Decisión
• Implementar una arquitectura monolítica desarrollada en Java.
• Toda la lógica de negocio, presentación e integración se ejecutará dentro de una única aplicación desplegada en un servidor empresarial.

• Justificación
• Garantiza consistencia transaccional ACID en todas las operaciones bancarias.
• Simplifica el desarrollo inicial y el proceso de despliegue.
• Reduce la complejidad tecnológica para el equipo disponible.

• Consecuencias
• Positivas: simplicidad inicial, confiabilidad y consistencia de datos.
• Negativas: aumento del acoplamiento, dificultad para escalar componentes individuales y tiempos de despliegue cada vez mayores.

• ADR-015: Migración Gradual del Monolito Java Core a Microservicios
• Estado: Propuesto (En evaluación).
• Contexto: El sistema monolítico ha alcanzado sus límites de escalabilidad y dificulta la incorporación de nuevas funcionalidades para los canales digitales.

• Decisión
• Adoptar una migración gradual utilizando el patrón Strangler Fig.
• Mantener temporalmente las operaciones financieras críticas dentro del monolito mientras se extraen módulos independientes como Consultas, Usuarios y Notificaciones.

• Justificación
• Reduce el riesgo de una migración completa tipo Big Bang.
• Permite modernizar el sistema de forma progresiva.
• Conserva la estabilidad de las operaciones bancarias críticas durante la transición.

• Consecuencias
• Positivas: menor riesgo de fallos, modernización gradual y mayor flexibilidad para futuras mejoras.
• Negativas: coexistencia temporal entre monolito y microservicios, aumentando la complejidad operativa y la necesidad de herramientas de observabilidad.

• Proceso de Adopción de ADRs en TechBank
• Estado: Aprobado.
• Objetivo: garantizar que todas las decisiones arquitectónicas importantes queden documentadas para futuras generaciones de desarrolladores.

• Paso 1 - Creación
• Todo cambio significativo en arquitectura, infraestructura, patrones o tecnologías deberá documentarse mediante un ADR en estado Propuesto.
• El responsable será un Arquitecto de Software o un Ingeniero Senior.

• Paso 2 - Revisión y Aprobación
• El ADR será revisado por el comité de arquitectura.
• La aprobación final corresponderá al Líder de Arquitectura o al CTO.
• Una vez aprobado, el documento será almacenado en formato Markdown dentro del repositorio Git del proyecto.

• Paso 3 - Auditoría y Revisión
• Los ADR deberán revisarse al inicio de cada trimestre o cuando cambien las condiciones del negocio, el rendimiento del sistema o los costos de infraestructura.
• Esto permitirá mantener la documentación vigente y alineada con la evolución tecnológica.

• Conclusión
• La adopción de ADRs proporciona un historial confiable de las decisiones arquitectónicas.
• Facilita el mantenimiento del software, mejora el proceso de incorporación de nuevos desarrolladores y reduce el riesgo de repetir errores del pasado.

• EJERCICIO 4 - ADR-001: Selección de Almacenamiento para Videos
• Estado: Aceptado.
• Contexto: El sistema de streaming debe almacenar grandes volúmenes de videos bajo demanda (VOD).
• Se evaluaron diferentes alternativas considerando costo, durabilidad, escalabilidad y disponibilidad.

• Alternativas Consideradas
• AWS S3 como almacenamiento de objetos administrado.
• Construir una CDN propia desde cero.
• Implementar un sistema de archivos distribuido como GlusterFS.

• Decisión
• Utilizar AWS S3 como almacenamiento principal y persistente para todos los archivos maestros de video.
• Los usuarios finales no accederán directamente a S3; el contenido será distribuido mediante una capa de caché.

• Justificación
• AWS S3 ofrece alta disponibilidad y una durabilidad del 99.999999999%.
• Permite almacenar grandes cantidades de información sin administrar servidores propios.
• Facilita la escalabilidad y reduce los costos de mantenimiento.

• Consecuencias
• Positivas: almacenamiento prácticamente ilimitado y alta confiabilidad.
• Negativas: el acceso directo desde los clientes genera mayor latencia y costos de transferencia, por lo que será necesario utilizar una CDN.

• ADR-002: Selección del Protocolo de Streaming
• Estado: Aceptado.
• Contexto: Una vez definido AWS S3 como almacenamiento, era necesario seleccionar el protocolo de transmisión de video compatible con navegadores y dispositivos móviles.

• Alternativas Consideradas
• HTTP Live Streaming (HLS).
• MPEG-DASH.
• RTMP.

• Decisión
• Adoptar HLS como protocolo principal de streaming.
• Los videos serán segmentados en archivos .ts y listas de reproducción .m3u8.

• Justificación
• HLS funciona sobre HTTP estándar.
• Es compatible con navegadores, dispositivos móviles y Smart TV.
• Se integra perfectamente con AWS S3 y con las CDN.

• Consecuencias
• Positivas: gran compatibilidad entre plataformas y facilidad de implementación.
• Negativas: introduce una latencia aproximada de entre 2 y 6 segundos, adecuada para video bajo demanda pero limitada para transmisiones altamente interactivas.

• ADR-003: Estrategia de Caché mediante CDN
• Estado: Aceptado.
• Contexto: Servir los segmentos HLS directamente desde AWS S3 incrementaría la latencia y los costos cuando miles de usuarios soliciten el mismo contenido.

• Alternativas Consideradas
• Amazon CloudFront.
• Varnish Cache.
• Redis.
• Otros servicios CDN.

• Decisión
• Implementar Amazon CloudFront como red de distribución de contenido (CDN).
• CloudFront almacenará en caché los segmentos de video y únicamente solicitará el contenido a AWS S3 cuando sea necesario.

• Justificación
• Reduce significativamente la latencia para los usuarios.
• Disminuye el consumo de ancho de banda y los costos de salida desde AWS S3.
• Mejora el rendimiento global del sistema.

• Consecuencias
• Positivas: reproducción más rápida, mejor experiencia de usuario y capacidad para atender millones de solicitudes.
• Negativas: será necesario administrar correctamente la invalidación de caché cuando cambien los archivos originales.

• ADR-004: Comunicación para Usuarios Concurrentes
• Estado: Aceptado.
• Contexto: La plataforma requiere mostrar información en tiempo real, como la cantidad de usuarios conectados y eventos del sistema, sin afectar el rendimiento del streaming.

• Alternativas Consideradas
• WebSockets.
• Server-Sent Events (SSE).
• HTTP Polling.

• Decisión
• Utilizar Server-Sent Events (SSE) para enviar eventos y métricas desde el servidor hacia los clientes.
• Las acciones del usuario continuarán realizándose mediante solicitudes HTTP REST tradicionales.

• Justificación
• SSE funciona sobre HTTP estándar y aprovecha la infraestructura existente.
• Consume menos recursos que WebSockets para comunicaciones unidireccionales.
• Facilita la escalabilidad y simplifica la arquitectura del sistema.

• Consecuencias
• Positivas: infraestructura más sencilla, mejor rendimiento y menor consumo de recursos.
• Negativas: la comunicación solo es del servidor hacia el cliente; para funcionalidades como chat en tiempo real será necesario incorporar WebSockets o WebRTC en futuras versiones.
